# Open questions and known gaps

The owning repo is in brackets. Resolve 2–5 first: they shape the CRDs, the protocol handshake and the database schemas.

1. **Repo hosting and process** [enzarb]: no git history or remotes yet. Decide hosting/naming, CI, release/versioning, and image registry. Pin toolchains: `mise.toml` uses `latest`, the sandbox uses `ubuntu:26.04`, and the Rust crates need lockfiles.
2. **AuthN/AuthZ** [ui, sandbox-proxy]:
   - the login provider;
   - the token format the UI issues and the proxy checks (JWT, signing keys);
   - mapping connector identities to enzarb users (`app_api.identity_v`).
3. **Proxy/executor → sandbox-init trust** [sandbox-container, sandbox-proxy, workflows]: mTLS or projected ServiceAccount tokens; NetworkPolicy blocking sandbox-to-sandbox traffic in the shared namespace (ADR-0013); per-Project egress policy.
4. **Secrets** [operator, connectors]:
   - where the Claude OAuth token (resolved: encrypted in Postgres, [database.md](database.md)) and the GitHub App private key live;
   - ~~whose Claude token pays for webhook-triggered runs~~ resolved: the Project owner's, one per user, encrypted in Postgres ([ADR-0004](adr/0004-claude-credentials.md) amendment 2026-10-13);
   - keeping tokens unreadable if sandboxes ever get Kubernetes API access (ADR-0013 limits it to other namespaces).
5. **Prompt injection** [workflows, connectors]: issue authors steer an agent that holds write credentials. Mitigations:
   - short-lived, single-repo clone tokens for each run;
   - only users with write access can approve;
   - the agent pushes to branches only, never to protected branches;
   - consider restricting triage on public repos to known actors.
6. **Worktree mode** [sandbox-container]: worktree slots per sandbox, cleanup, and conflicts with someone working interactively in the same sandbox. **Fresh mode** depends on agent-sandbox warm pools/claims; confirm the upstream API in v0.5.x.
7. **Container runtime in the sandbox** [sandbox-container]: resolved by ADR-0012 and ADR-0016 (rootful dockerd inside the sandbox container under gVisor; rootless is not used). Still open: CPU/memory quotas per sandbox and per run. dockerd and inner containers share the sandbox container's limits, so a heavy build can OOM the agents too. Image pruning on the docker volume is tracked separately.
8. **Proxy availability** [sandbox-proxy, proto]: websockets are stateful. Running several replicas needs reconnect and resume semantics in the protocol and timeouts on flow-control credit. Workspace persistence (PVC lifecycle, hibernate/resume) is also open.
9. **pgop for a durable engine** [kubernetes, pgop]: max 1 replica; backups, PITR and pooling aren't documented. LISTEN needs a direct session-mode connection. Confirm whether object-level grants are possible in pgop. See [database.md](database.md#known-pgop-gaps-for-this-use).
10. **Transcript storage** [workflows, sandbox-container]: resolved as Postgres (`engine.session_events`, ADR-0022), shown on the task page. Open: retention. Events are kept forever per Project by default; monthly partitions allow dropping old ones.
11. **Observability** [all]: tracing from connectors → workflows → sandbox, with the delivery id as the correlation id; sandbox utilization metrics (decided in [ADR-0019](adr/0019-sandbox-utilization-polling.md): workflows polls sandbox-init, stored in Postgres; open until implemented); workflow admin views for stuck items, retries and dead jobs; audit of terminal sessions; limits on Claude usage and CPU.
12. **CRD versioning** [operator]: a conversion strategy for `v1alpha1`, and status conditions designed so the UI's boot checklist maps 1:1 to them.
13. **Testing** [all]:
    - table tests for pure transitions;
    - engine tests against real Postgres (testcontainers);
    - shared `proto/` test vectors for Rust and TS;
    - operator envtest;
    - end-to-end on kind with recorded webhook fixtures, plus a smee-style relay for live GitHub.
14. **SvelteKit remote functions** [ui]: they are still behind an experimental flag (`experimental.remoteFunctions`). Pin versions. Browsers connect to `sandbox-proxy` directly for websockets.
15. **Human review before merge** [workflows]: should `ReadyToMerge` also require a human GitHub review? Current decision: no. Only enzarb's own review approval is required, and the user's Merge click is the human gate.
16. **Billing traceability for sandbox usage** [workflows, ui]: the raw samples (`workflows_api.sandbox_stats_v`) are pruned after `sandboxStatsRetentionDays` (default 90, [ADR-0019](adr/0019-sandbox-utilization-polling.md)) and capped per sandbox, so they are a monitoring window, not a billing record. A longer-term record needs its own design: durable rollups (for example hourly per project and sandbox, written by the poller before the prune), the sandbox, task or run each belongs to, a much longer or no prune horizon, and a stable versioned `workflows_api` object for it. The Metrics tab charts the short window only. Needs an ADR before implementation.
17. **Graph tasks outside `workflow = 'issue'` queries** [workflows, ui]: `graph:issue` items ([ADR-0020](adr/0020-graph-workflows.md)) are not seen by some code that filters on `workflow = 'issue'`: the ticker's issue sweeps (nudges, stale; a definition can use a `timer` wait instead). Epic intake, the dependency sweep and stacking now include them, and Needs you and the board classify graph tasks from `state_data.wait` (an approval wait shows as `approval`, a merge wait as `merge`). `graph:change_request` items are not covered by the compiled-only stacking (a stacked change request stays compiled, and a graph change request is never chosen as a stack parent), the GitHub sync sweep, or the task page's merge checklist. Until those learn `graph:%`, a repository that opts in loses those behaviours for its issues, including compiled issues that move to the graph on approval or retry. A failed graph task can be retried (it restarts at `start`), so `Failed` is no longer final.
18. **Graph workflow rollout and rollback** [workflows, sandbox-container]: a workflows build without graph support cannot read `graph:*` work items (`WorkflowState::from_row` errors, so their events stay unprocessed) or run `agent_segment` jobs (unknown kind, failed permanently). Rolling workflows back after a repository opted in strands its graph tasks; roll back only with no `graph:*` item open, or cancel them first. A sandbox-container older than `RunStart.graph` runs a segment as a plain agent run with a "too old" prompt and its result has no graph, so the task fails with a clear error: deploy sandbox-container before a repository opts in. The same holds for a change request definition: its events (`pushed`, `conflict`), actions and wait options (`after`, `reason`, `text`) need a sandbox-init built with the same `enzarb-graph`, or the sandbox rejects the definition. In a change request graph the automatic-round cap is a node's `max_visits`, counted per task instead of per streak since a person last acted (the compiled `ENZARB_MAX_AUTO_ROUNDS` does not apply). Of the cheaper review rounds (#202), graph change requests get the delta re-review (`{previous_reviewed_sha}` from `prior_review`, `stats.review_rounds`/`fix_rounds`) and the prepare context (#205: merge base, affected components, for every segment), but not the mechanical shortcut (a separate `mechanical_check` job, not a prompt; a definition would need a node for it) nor `stats.agent_secs`.
19. **Secrets readable by the agent without a permission policy** [sandbox-container, operator]: since the ADR-0011 amendment of 2026-10-15 every agent permission request is allowed, so what the agent uid (`enzarb`, uid 1000, the same uid as sandbox-init) can read is bounded only by what is passed or mounted. Not readable: the clone/push token (never in the agent's environment, stripped from `request.json`, passed only to sandbox-init's own short-lived git processes as `GIT_CONFIG_*` environment). Readable: the Claude token (its own environment and the legacy `/workspace/.enzarb/claude-token`); a job's `deps_token`/`npm_token` (agent environment, `ENZARB_DEPS_TOKEN`/`NODE_AUTH_TOKEN`); a CI-fix run's read-only `GH_TOKEN`; the mux auth token at `/var/run/enzarb/auth/token` (mode 0400, owned by the pod's uid); `/workspace/.enzarb/runs/*/callback.json` of runs started by a workflows executor older than `run_results` (callback URLs and bearer tokens; runs started over a `run_results` session have none, see #20); other chats' transcripts; and, while they run, the environment of other same-uid processes through `/proc/<pid>/environ`, which includes a concurrent push's `Authorization` header (sandbox-init itself is non-dumpable; not verified under gVisor). Closing these needs a separate uid for the agent (or not mounting the auth token into the agent's reach), not filtering.
20. **Remove the run-finished HTTP callback** [workflows, sandbox-container, proto, helm]: since `run_results` (ADR-0008 amendment of 2026-10-15) results are pulled over the mux and new runs carry no callback token. The callback endpoint (`POST /v1/runs/{run_id}/finished`, `ENZARB_EXECUTOR_CALLBACK_SECRET`, `ENZARB_EXECUTOR_URL`) and sandbox-init's callback delivery stay only until every sandbox runs a sandbox-container with `run_results`; a follow-up removes them (deprecate the chart values first). Also: the stored result (`state.json`) is still agent-writable (same uid, #19), so a run's `summary`/decision can be forged by its own agent; only the push facts are verified against the remote.
21. **Finding to filed-issue link** [workflows, ui]: the platform view (`/platform`) shows a link to the GitHub issue a finding filed only when `FindingRow.issueUrl` is set, but `engine_api.finding_v` has no issue column and `file_issue` has no lookup by key, so it is never set. It needs a column or lookup in `finding_v`. The view also polls (every 30 s and on each change-stream event) because the kernel does not `NOTIFY` when a finding is raised or cleared; a `NOTIFY` on `engine.findings` writes would make it live.
22. **`network` and `load` environment failures do not wait in the library** [workflows]: the library's agent steps list `platform_wait` for `disk_full` and `oom` only ([ADR-0026](adr/0026-platform-wait.md)). The only fact that could end a `network` or `load` wait is `sandbox.healthy`, which is true whenever the sandbox reports, so the wait would end on the next tick, the step would fail again and the task would loop with no cap or backoff. These kinds keep the step's edges (`review/rounds/human`, `implement/blocked`, ...). Waiting on them needs a fact that tells network or load recovery (for example a probe result or a load average) or a backoff.

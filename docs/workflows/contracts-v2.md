# Engine v2 contracts (ADR-0022)

This file is the shared interface for the parallel milestones:
- **M3–M5:** engine, sandbox and connectors;
- **M6:** UI;
- **M2:** library.

The interpreter types in `workflows/crates/flow` (`TaskState`, `TaskEvent`, `Effect`, `RunStep`, `Projection`, `TaskDocument`) are authoritative. This file only adds storage and the read API. Change it in the same commit as the code that needs the change. The migrations in `workflows/migrations/2026101600000*` are the implementation.

## Postgres schema `engine` (owned by workflows; replaces `workflows`/`workflows_api`)
| Table | Columns (key ones) | Notes |
|---|---|---|
| `tasks` | `id bigserial`, `project text`, `repo text`, `binding text`, `workflow_ref text`, `state jsonb` (TaskState), `resolved jsonb` (Resolved, pinned), `origins jsonb`, `started_by`, `created_at`, `updated_at`, `ended_at` | `state` and `resolved` are opaque to everything but the engine. `started_by` is the login whose event started the task (user-scope secrets) |
| `subjects` | `task_id`, `kind text` (issue, pull_request, chat_thread), `key text` (`github:o/r#n`), `url`, `linked_at`, `ended bool` | An object belongs to at most one live task (unique index on `key` where not `ended`) |
| `relations` | `task_id`, `kind text` (parent, child, blocked_by), `target_key text` (a subject key or `task:<id>`), `source text` | A row reads "task **is** `<kind>` **of** target": an epic's `relate: {kind: parent}` rows make it the parent of each sub-issue; `(C, child, E)` says the same from the child. `blocks` is derived. Bindings see them as `relations: [{kind, task, workflow, status, phase, node, vars}]` of the event's object, `kind` being the related task's role (an epic is `parent` of its sub-issue); a PR's referenced issues' tasks come as `references` |
| `events` | `id bigserial`, `dedupe_key text unique`, `project`, `subject_key`, `task_id null`, `type text`, `payload jsonb`, `received_at`, `processed_at`, `note` | The inbox. `type` is a catalog type (payload = a catalog `Event`), `ui.<kind>` (from `submit`) or `engine:<kind>` (payload = a `TaskEvent`). Unrouted events are processed with no task and a `note` (kept for audit) |
| `transitions` | `task_id`, `event_id`, `from_state jsonb`, `to_state jsonb` (`{status, node, pending}`), `effects jsonb`, `at` | Append-only, used for replay |
| `jobs` | `id`, `task_id`, `project`, `kind text` (run_step, steer, stop_step, call_action, refresh_fact), `input jsonb`, `status` (queued, running, done, blocked), `attempt`, `run_after`, `lease_owner`, `lease_until`, `output jsonb`, `error`, `idempotency_key unique`, `priority int`, `concurrency_group text null`, `concurrency_max` | The generic executor queue. One backoff (`base·2^n`, capped at 10 min) for infrastructure errors; `blocked` waits on a human (a missing secret) until `resume` |
| `timers` | `task_id`, `timer_id`, `fire_at`, `fired` | `SetTimer` → absolute wake → `Timer` event |
| `step_runs` | `run_id text pk`, `task_id`, `project`, `node`, `step`, `attempt`, `runtime`, `model`, `queued_at`, `started_at`, `ended_at`, `last_activity_at`, `active_secs`, `queue_secs`, `exit`, `tokens jsonb` (`{input, output, cache_read, cache_creation, models}`), `cost_usd numeric`, `resumes int`, `stalls int`, `steers int`, `sandbox jsonb` | Metrics (ADR-0022 §10) |
| `session_events` | `run_id`, `seq int`, `at`, `kind text` (prompt, user, assistant, thinking, tool_call, tool_result, usage, steer, system, stdout, stderr), `payload jsonb`, `truncated bool`, PK `(run_id, seq, at)` | Partitioned by month on `at` (plus a default partition); GIN index on `payload`; redacted before insert; payload capped at 1 MB (head and tail) |
| `facts` | `task_id`, `name text`, `value jsonb`, `source text`, `at`, `unknown_refreshes int` | Verified only (git, GitHub). `unknown_refreshes` counts consecutive refreshes that left the value null (unknown) and resets on a known value |
| `secrets` | `scope text` (user, project, instance), `owner text` (`''` for instance), `name text`, `ciphertext bytea`, `pending text`, `updated_at` | AES-256-GCM, `nonce(12) ‖ ciphertext+tag`, key `ENZARB_SECRETS_KEY` (32 bytes, base64, from a Kubernetes Secret). `secret_set` writes `pending`; the engine encrypts it on its next tick. A declared secret `{name, scope, env, file}` is looked up in its own scope only; the **user** is the Project owner (`spec.owner`). At user scope the name `ENZARB_CLAUDE_SECRET_NAME` (default `claude_token`) falls back to the UI-captured `app.claude_credentials` row of that user (`app_api.claude_credential_get`, keyring `ENZARB_CLAUDE_KEYRING_DIR`). A missing secret blocks the job and pauses the task until `resume` |
| `projection` | `task_id pk`, `project`, `repo`, `workflow`, `title`, `subjects jsonb`, `status`, `end_status`, `phase`, `node`, `column`, `waiting_on text`, `reason`, `text`, `actions jsonb`, `commands jsonb` (additive: `[{name, label, description?, from}]`, the commands that apply now), `artifacts jsonb`, `needs_you bool`, `cost_usd`, `created_at`, `updated_at` | Written in the same transaction as each transition. **The UI's only task source.** `NOTIFY engine_projection, '<task_id>'` |
| `findings` | `key text pk` (`<check id>:<task id>`, or `<check id>:<project>`), `task_id null`, `project`, `check_id`, `kind` (dead_wait, platform_failure, event_failing), `severity` (info, warning, critical), `text`, `first_seen`, `last_seen`, `cleared_at null` | Liveness findings (ADR-0024). Written only by the `platform` pass; observation only. Cleared rows are kept; a returning condition reopens the same key |
| `resolutions` | `project`, `repo`, `board jsonb`, `view jsonb`, `updated_at` | What the engine last resolved, for `board_v`/`workflow_v` |
| `chats` | `run_id` (`chat-<id>`), `project`, `user`, `title`, `started_at` | Chats are not tasks |
| `sandbox_stats` | `project`, `sandbox`, `at`, `run_ids text[]`, cgroup counters | Samples attributed to the step runs running at the time |
| `sandbox_holds` | `project`, `generation`, `since` | No new step starts while a sandbox roll is pending |

Facts: `facts.dependencies` is `null` until known and a list (possibly `[]`) once known; the engine fills it when a task starts. `ci`, `mergeable` and `reviews` are refreshed on every verified change of the open PR's head (webhook head == GitHub's head; foreign pushes included: a `push` to a live task's PR head branch routes to that task). `release`, `tag`, `package` (tag `v<version>`) and `deployment` (its sha) events without a subject go to every live task whose merge commit (`Subject.merge_sha`, from the merged `pull_request` event) the ref contains (connector compare: not ahead of the ref); for `release`/`tag`, `facts.contained_in_tag` is set to the tag first.

Steering: a UI `steer` while a step runs (and the step's or wait's `steer` matches) reaches the agent as a user turn. At a wait there is no session: the steer is a `comment` event on the task (body = the text) and the wait decides; e.g. the library's plan approval treats it as feedback and revises the plan.

NOTIFY channels: `engine_projection` (task id), `engine_events` (inbox id, wakes the reducer), `engine_session` (`<run_id>:<seq>`).

## Read and write API (schema `engine_api`, SQL, SECURITY DEFINER)
- **Projection reads:**
  - `engine_api.task_v`: projection columns plus `repo`, `workflow_ref`, `created_at`, `ended_at`; `artifacts` without `content`; and `findings` (additive, last column): the task's open findings as `[{key, check, kind, severity, text, first_seen, last_seen}]`, highest severity first. `reason` and `text` are computed on read: the interpreter's `reason`/`text` when its `reason` is non-empty, otherwise the top open finding (`reason` = its check id, `text` = its text; the interpreter's `text`, if any, still wins). The stored projection is never written by findings, so a reducer transition cannot make a finding flicker;
  - `engine_api.finding_v`: all open findings, `(key, task_id, project, check_id, kind, severity, text, first_seen, last_seen)`; `task_id` is null for platform-scope findings (the platform view);
  - `engine_api.task_detail(task_id) -> jsonb`: the `task_v` row plus `artifacts` (with content), `transitions` (`[{at, event_type, from: {status, node}, to: {status, node}, effects: <count>}]`), `step_runs` (table columns), `facts` (`{name: value}`) and `relations`.
- **Session reads:** `engine_api.session_v(run_id, after_seq, limit)` returns `(seq, at, kind, payload, truncated)`; `engine_api.session_search(project, query)` returns `(run_id, task_id, seq, at, kind, snippet)`.
- **Board:** `engine_api.board_v(project) -> jsonb` `{columns: [{id, title, limit}], defaults}` (empty columns until something resolved).
- **Workflow viewer:** `engine_api.workflow_v(project, 'owner/repo') -> jsonb` `{bindings, workflows: [{ref, origin, description, phases: [{id, use, origin, params, with, exits, routes, graph: {nodes, edges}}], origins}], lint: [errors]}` or null.
- **Metrics:** `engine_api.metrics(project, from, to)` returns `(workflow, phase, step, runs, avg_wall_secs, active_secs, queue_secs, input_tokens, output_tokens, cost_usd, retries, resumes, stalls, steers)`.
- **Write path:** `engine_api.submit(task_id, actor jsonb, kind text, data jsonb) -> event_id`, kind one of `command` (`{command, args}`), `comment` (`{body}`), `cancel`, `resume`, `stop`, `steer` (`{body}`). It inserts an inbox event of type `ui.<kind>` (`{source: ui, actor, kind, data}`). The engine turns it into a `comment` catalog event on the task (`/command args`, `/stop`, `/cancel`, or the body), with `actor.can_write` filled from GitHub; `resume` resumes a paused task (writers only) and re-queues jobs blocked on a human. The UI never validates state.
- **Secrets:** `engine_api.secret_set(scope, owner, name, plaintext)`, `secret_list(scope, owner) -> (name, updated_at)` (names only), `secret_delete(scope, owner, name) -> boolean`.
- **Chat:** `engine_api.chat_v(user) -> (run_id, project, title, started_at, last_at, events)`; chat sessions use `session_events` with `run_id` `chat-<ACP sessionId>`. They are written by sandbox-proxy (role `enzarb_sandbox_proxy`), which observes the relayed `acp` channel: `engine_api.chat_record(run_id, project, user, title)` (title = first prompt line) and `engine_api.chat_event(run_id, kind, payload) -> seq` (`user` prompts; `session/update` as assistant, thinking, tool_call, tool_result or system; Claude tokens redacted; over 1 MB keeps head and tail).
- **Connector receiver:** `engine_api.ingest(dedupe_key, project, subject_key, type, payload) -> bigint` (NULL for a duplicate), and `engine_api.secret_for_receiver(project, name) -> (ciphertext, pending)` for the custom-event HMAC.

Grants (in the migration, re-asserted each tick by `engine.apply_grants()`): `enzarb_ui` gets `task_v`, `finding_v` and the UI functions; `enzarb_connectors` gets `ingest` and `secret_for_receiver`; `enzarb_realtime` gets `CONNECT`, `task_v` and `finding_v`; `enzarb_workflows` gets the `engine` tables.

## Liveness findings and the `platform` source (ADR-0024)
`platform` is an **internal** event source: a periodic pass of the ticker (`ENZARB_FINDINGS_SECS`, default 60). It has no task-event payload, is not in `event.json` and never reaches the interpreter. It evaluates the `checks/*.yaml` of each Project's library (format: [format.md](format.md#checks), schema [`schemas/check.json`](schemas/check.json)) and brings `engine.findings` in line:
- **Evaluate** is pure (checks + a snapshot of task facts, clocks, relations, commands and platform facts → desired findings). **Reconcile** is the only writer and writes `engine.findings` (and the fact refresh keeps `facts.unknown_refreshes`). When a finding opens and its check has an `issue:`, reconcile also inserts one `engine.jobs` row of kind `file_issue` (`task_id` null for platform scope), idempotent on `finding:<finding key>`, in the same transaction. Tasks, projection, events, transitions, timers, step runs and other jobs are never written.
- A finding is raised when the condition held on two consecutive passes, refreshed while it holds, and cleared (`cleared_at`) when it stops or the task ends. A check whose platform fact is unknown neither raises nor clears.
- A finding never cancels, stops, restarts, nudges or times out anything, and sends no notification.
- Platform facts (`workflow_run.status`, `chart.deploy_state`, `sandbox.disk_pct`, `sandbox.mem_working_set_pct`, `project.pending_change`, `sandbox.healthy`) come from a provider. Wired: `sandbox.disk_pct` (latest `sandbox_stats` sample, at most 10 minutes old), `sandbox.mem_working_set_pct`, `sandbox.healthy` (a sample at most 10 minutes old exists) and `project.pending_change`. `workflow_run.status` and `chart.deploy_state` come from the connector and the updater when they are configured, else unknown. `sandbox.mem_working_set_pct` is unknown without a memory limit.
- The change stream does not push when a finding is raised or cleared; it shows on the next read or projection change.

## Platform wait (ADR-0026)
- **Step key** `platform_wait: [{kind, until}]` (additive). `kind` is `disk_full`, `oom`, `network` or `load` (the `step_finished.environment.kind` values the sandbox can resume); `until` is a `platform`-only condition (`all`/`any`/`not` over `platform: {fact, op, value}`). A finish whose `environment.kind` is listed puts the task in a platform wait instead of following edges or retrying.
- **State** (additive optional fields of the task state): `platform_wait: {kind, detail, until, waits}` and `platform_waits`. `status` and `pending` are unchanged. Projection: `waiting_on: external`, `reason: platform_wait`, `needs_you: false`.
- **Internal event** `platform_cleared {run_id, wait}` (engine source like `timer`; not in the public event catalog). Produced by the ticker pass `wake_platform_waits` when `until` holds (unknown facts keep waiting), deduped on `wake:<task>:<wait>`. Accepted only for the pending run with `wait` equal to the current count; the interpreter then emits `RunStep` with the same `run_id`/`attempt` (field `resume` = wake count, additive), and the executor re-sends `step_start`.
- **Check leaf** `platform_wait: {kind?}`: the task is in a platform wait (of that kind). Task scope only.
- **Check leaf** `event_failing: {for?}`: the task has an unprocessed event that failed at least once, for at least `for` since it was received (any duration when omitted). Task scope only; the issue text may use `{attempts}` and `{error}`. See the checks table in [workflows.md](../workflows.md#liveness-checks).
- No timeout, no retry budget, no escalation by age; `/cancel` still ends the task.

## Sandbox protocol (proto)
Defined in `proto/crates/enzarb-proto/src/step.rs` and mirrored in `proto/ts`; features `steps`.
- **Step frames:**
  - `step_start {run_id, attempt, task_id, workspaces: [{repo, url, mode, branch, base, push, token}], exec: agent{runtime{name, install, protocol, command, env, capabilities}, model, prompt, result_schema?} | command{run, tools}, outputs{name: {file, format, optional}}, env{NAME: secret}, files{path: secret}, github_token?}` → `step_accepted {run_id, state, existing}`. `files` (additive) are written `0600` under the primary workspace, excluded from commits (`.git/info/exclude`), redacted and removed when the step ends. A workspace's `branch`/`base` come from the step's `workspaces` entry (templated) when set, else the PR head or `enzarb/task-<id>`, and the default branch. Steps have **no time limit** in the sandbox; stall detection in the engine pauses;
  - `step_steer {run_id, text}`; `step_stop {run_id}`; `step_resume {run_id}`;
  - `step_status {run_id, after_seq}` → replayed `session_event`s, then `step_state {run_id, state: running|interrupted|finished|unknown, result?}`, and subscribes the session;
  - `session_event {run_id, seq, at, kind, payload, truncated}` (streamed);
  - `step_finished {run_id, exit, outputs{}, result?, git: [{repo, branch, head_sha, pushed}], usage?, environment?: {kind, detail}, error?}`. `environment` (additive, optional; old decoders ignore it) says the step failed because of its environment, not the code; `detail` is free text of what was observed. `kind` is one of `disk_full` (a filesystem ran out of space or inodes; e.g. `/workspace: 0 bytes free`), `oom` (a process was killed for exceeding its memory limit; e.g. `cargo killed by SIGKILL, memory.events oom_kill=1`), `toolchain_missing` (a tool the step needs is not installed; e.g. `cargo: command not found`), `network` (DNS, connect or timeout failure; e.g. `could not resolve github.com`), `load` (the node was too loaded to finish in time; e.g. `load average 40 on 4 CPUs`), `unknown` (a kind this consumer does not know; treat it as a generic environment failure; decode-only, never sent).
- **Flow conditions and templates:** the engine forwards `step_finished.environment` to the interpreter, which binds it as `last.environment` (`{kind, detail}`, `kind` being the snake_case string above, `unknown` included). It is `null` when the step reported none, so `last.environment.kind == 'disk_full'` and `last.environment == none` are both safe. Scenario stubs take it as `environment: {kind, detail}`.
- **Resume:** the sandbox never persists secrets. After a sandbox restart a running step is `interrupted`; the engine re-sends `step_start` with the same `run_id`, which continues it (ACP `session/load`), never restarts it. (`step_resume` without secrets answers `error {code: secrets_required}`.)
- **Git facts** are re-verified by the engine (`branch_head == head_sha` on GitHub) before `StepFinished` reaches the interpreter; `result` is validated against its schema (invalid → exit `failure`).
- **Chat:** `chat_*` frames as before (ADR-0014), captured as `session_event`s of run `chat-<id>`.

## Connectors (M5)
- **Event catalog:** `connector-github::catalog::map` maps each webhook to a `flow::events` catalog event; the receiver calls `engine_api.ingest`. Signed custom events: `POST /v1/events/<project>`, `X-Enzarb-Signature: sha256=<hex hmac>`, key = Project secret `ENZARB_EVENTS_SECRET_NAME` (default `events_hmac`); payloads are validated against the workflow's declared schema by the engine.
- **Generic actions** (engine `actions.rs`; targets default to the task's subjects, `number`/`repo` override):
  - `comment`, `label`, `unlabel`;
  - `open_pull_request` (links the PR as a subject), `update_pull_request`, `merge_pull_request` (a refused merge, e.g. "Pull Request has merge conflicts" or "Base branch was modified", finishes `ok: false` with the provider's text in `result.error`; no `message` or `reason` is set);
  - `create_issues` (result `{issues: [{kind: issue, repo, number, title, url, key}]}`), `open_pull_request` (result `{kind: pull_request, repo, number, title, url, subject}`), `close_issue`, `set_base`, `update_branch`, `delete_branch`;
  - `file_issue` (args `repo?`, `title`, `body`, `key`, `labels?`; result `{kind: issue, repo, number, title, url, key, outcome: created|updated|unchanged}`): files one issue under a stable `key`; see `docs/contracts.md`, "`file_issue`";
  - `read_file`, `resolve_ref`.
- **Facts:**
  - `ci` `{sha, state, failing: [{name, kind, url, conclusion, log_excerpt, actionable, job_id?, run_id?}]}` (ignore regex `ENZARB_CI_IGNORE_CHECKS`);
  - `reviews` (the list `[{author, state, body}]`: latest review per author, lowercase state), `mergeable` (`null` until GitHub has computed it), `merged`, `git`, `dependencies`; `contained_in_tag` (see Facts above).
- **Instance:** task documents carry `instance: {bot: {login, handle}, url}` from `ENZARB_BOT_LOGIN`, `ENZARB_BOT_HANDLE`, `ENZARB_PUBLIC_URL`; a comment's `mentioned` is recomputed with `ENZARB_BOT_HANDLE`.
- **Auto-upgrade:** the definition is re-resolved (with the binding's `with:` params) at each wait and before each step (also when the event finishes the step or action in flight); a running step keeps its definition.

Contract tests and the registry that maps each action promise to its test: `docs/workflows/contract-tests.md`.

# 0017. Work item dependencies

## Context
Issues and PRs often must wait for other work. Without a model for that, a PR whose prerequisite is unmerged can reach `ReadyToMerge` and be merged out of order.

## Decision
- **Where they are declared.** GitHub's native "blocked by" relationships (read through `Connector::list_dependencies`, written through `add_dependency` / `remove_dependency`), and `Depends on #N` / `Blocked by #N` / `Depends on owner/repo#N` text in a body or comment (`enzarb_connector::dependencies`, a pure parser: case-insensitive, lists, no code blocks or quoted lines, no prose such as "depends on the #1 priority").
- **Storage.** `workflows.work_item_dependencies(work_item_key, depends_on_key, source, created_at)`, `source` one of `github`, `text` (body) or `comment`. Each source replaces only its own rows (a comment only adds, and only a commenter with write access counts, so nobody else can close the merge gate; the connector has no comment edit or delete events yet, so retracting a comment dependency is part of the removal path deferred to the UI PR), so sources never overwrite each other and cannot loop. A key with no work item yet is `pending`. Keys, not ids, because a dependency can be declared before either item has a row. Only dependencies inside one Project are stored; others are ignored and logged. A self dependency is dropped.
- **Inheritance.** A change request inherits the dependencies of the issue its body closes (`Closes|Fixes|Resolves #N`). It is computed in the view `workflows.effective_dependencies`, never copied.
- **Done.** A dependency is done when its work item is `Done` (issue) or `Merged` (change request). `Cancelled`, `Closed` and `Duplicate` are *closed without completing*: the dependent stays blocked with that reason, and a maintainer removes the dependency. A missing item stays `pending`.
- **Merge gate.** `Readiness` has a fourth check, `dependencies`. `all_ok` requires it; `needs_check` ignores it, so it never calls the connector. The reducer reads the open set into `Ctx::open_dependencies` for every event, so the merge action sees it fresh. `CrData.open_dependencies` stores it for the views (`work_item_v.blocked_by_dependency`, `state_data.checklist.dependencies`).
- **Auto-continue.** The ticker sweeps change requests, and emits `DependenciesChanged` when the open set differs from the stored one; the machine re-runs `evaluate`. A missed webhook delays this by one sweep.
- **Cycles.** `workflows.dependency_cycle(key)` (recursive CTE) finds a shortest cycle through an item. Members get an open dependency whose problem is `dependency cycle: #1 → #2 → #1`; the merge gate stays closed.
- **GitHub sync.** The ticker lists the native relationships of 50 active items every five minutes, rotating through them by id (about 600 calls an hour, so the GitHub rate limit stays available to readiness checks and agent runs), and replaces the `github` rows. A connector without the capability, or a token without access, is skipped: the feature degrades to text-only.
- **Stacking** (#107). A change request can build on its parent's change request instead of waiting for it. Only a single-parent chain is stacked: exactly one dependency is not completed, it has an open change request, and that request's branch is enzarb's own. The child branch starts from the parent's branch and its change request opens with that branch as base (`state_data.stacked_on`, `stack_parent_ref`, `stack_parent_tip`, `default_base`). The `dependencies` check keeps the child from merging into the parent's branch. After the parent is squash-merged, one `retarget_change_request` job rebases enzarb's own child branch with `git rebase --onto <default> <stack_parent_tip>`, pushes with `--force-with-lease=<branch>:<expected sha>` and sets the base with `Connector::set_base`. A plain rebase or merge of the base is wrong after a squash (it replays the parent's commits), and changing the base alone leaves the parent's changes in the child's diff. **Invariant:** this push is the only one in enzarb that rewrites history. It is made by the sandbox retarget run, only to an `enzarb/` branch that is neither the default nor a protected branch, only at an expected sha, and only when every commit it replays was authored by enzarb. A conflict, foreign commits or a stale parent tip push nothing and park the item under Needs you; retargeting never merges. A parent closed without merging leaves the child blocked.

## Consequences
- Shared contracts stay additive: a table, functions, views, one trailing column on `work_item_v`.
- Closing an issue as completed without a PR does not mark it `Done` (the issue machine treats any close as `Cancelled`); a dependency on such an issue reads as closed without completing until the dependency is removed.
- Not yet built: the start gate (a per-Project setting that holds implementation), the planning prompt block, and the UI. They follow in separate PRs.

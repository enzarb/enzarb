# 0013. One shared sandbox namespace; no Kubernetes API access from sandboxes

Supersedes the tenancy part of [ADR-0002](0002-sandbox-tenancy.md): one Capsule Tenant per owner, one namespace per Project, and a capsule-proxy kubeconfig inside each sandbox.

## Context
The first real deployment (oldie) showed that per-Project namespaces placed into per-owner Capsule Tenants need the operator to own every Tenant, and that the model buys little: sandboxes do not need the Kubernetes API for the current scope (ADR-0006), and the isolation that matters (gVisor, ADR-0012; NetworkPolicy; separate volumes and credentials) does not depend on namespaces.

## Decision
- **One namespace for all sandboxes:** `enzarb-sandboxes` by default (chart value `sandbox.namespace`), created by the Helm chart and separate from the release namespace (`enzarb`). It is labelled `pod-security.kubernetes.io/enforce: privileged`, which the dockerd sidecar needs (ADR-0012; gVisor is the boundary), so a stricter cluster default cannot reject sandbox pods.
- **Operator permissions:** cluster-scoped access to Projects only (get/list/watch/patch, `projects/status`, `projects/finalizers`); everything else through a Role in the sandbox namespace (Secrets, PVCs, NetworkPolicies, Sandboxes). It watches Sandboxes in that namespace (other owned objects are re-checked on every reconcile) and has no namespace or Tenant permissions.
- **Per-Project object names** in that namespace, all prefixed so they cannot collide and all labelled `enzarb.dev/project=<name>`:

  | Object | Name |
  |---|---|
  | Sandbox (agent-sandbox names its pod and headless Service the same) | `sb-<project>` |
  | Auth Secret | `sb-<project>-auth` |
  | Workspace PVC | `sb-<project>-workspace` |
  | Docker PVC | `sb-<project>-docker` |
  | NetworkPolicy | `sb-<project>` |

  The operator sets a controller ownerReference to the (cluster-scoped) Project on the Sandbox, Secret, both PVCs and the NetworkPolicy (the Secret and PVCs have none today), so deleting a Project garbage-collects them, including the volumes and their data; the headless Service is owned by the Sandbox through agent-sandbox. Before reusing an existing object the operator requires its controller ownerReference UID to equal the Project's UID and no `deletionTimestamp`; otherwise it reports `ResourcesReady=False, reason Terminating` and requeues, so a Project re-created under the same name never picks up its predecessor's Secret or volumes. An object with no controller ownerReference at all (created by hand) is never garbage-collected, so it is a terminal `NotOwnedError` naming the object for an admin to delete.
- **Name limit:** `sb-<name>` is the Sandbox, the pod hostname and the headless Service, so it must be a DNS-1035 label (the prefix guarantees it starts with a letter). Capping Project names at **50 characters** (DNS label) keeps every derived name, the longest being `sb-<name>-workspace`, within 63 characters. Enforced in the CRD (create-only CEL validation on `metadata.name`, so existing objects can still be updated and cleaned up), by the operator (`InvalidSpec`) and in the UI.
- **No Kubernetes API access from sandboxes, for now:** sandbox pods use a dedicated ServiceAccount `enzarb-sandbox` (created by the chart before any Sandbox) with `automountServiceAccountToken: false` on both the ServiceAccount and the pod, `enableServiceLinks: false`, no projected token volumes, no RBAC bindings and no kubeconfig. Without credentials the API is unusable; as defence in depth the egress policy also excludes the cluster's pod, service and node CIDRs (which contain the API server endpoint). **Any future API access will be limited exclusively to other namespaces** (for example per-Project work namespaces), granted through RoleBindings in those namespaces only; a sandbox will never get permissions in `enzarb-sandboxes` or in the release namespace.
- **What lives in the shared namespace:** only the per-Project objects above, the chart's ServiceAccount `enzarb-sandbox`, the auto-created `default` ServiceAccount (unused: every sandbox pod names `enzarb-sandbox`) and the chart's policies and LimitRange. No other Secrets: the proxy may read every Secret there.
- **Isolation inside the shared namespace:**
  - a chart-owned default-deny NetworkPolicy for the whole namespace (ingress and egress), so a pod without its own policy can do nothing and no single Project owns the namespace-wide rule;
  - a per-Project NetworkPolicy `sb-<project>` selecting only that Project's pod (`enzarb.dev/project=<name>`): ingress TCP 7070 only from the sandbox-proxy pods in the release namespace; egress DNS (UDP/TCP 53) to the cluster DNS pods only (`kube-system`, `k8s-app=kube-dns`; configurable for NodeLocal DNSCache), TCP 443 to `0.0.0.0/0` and `::/0` **except** the cluster CIDRs (chart value `sandbox.egress.clusterCIDRs`, required: pod, service and node networks). Sandboxes cannot reach each other, the API server, or other in-cluster services.
- **Status and conditions** (contracts section 2): `status.namespace` is the shared namespace; `status.sandbox` names the per-Project Sandbox, endpoint and auth Secret. The boot conditions are `ResourcesReady` (auth Secret, volumes, NetworkPolicy), `SandboxReady`, `Ready`; `TenantReady` and `NamespaceReady` are removed (they disappear on the next status write) and the UI checklist follows. An invalid spec is reported as `ResourcesReady=False, reason InvalidSpec`.
- **Consumers** (sandbox-proxy) find the sandbox only through `status.namespace` and `status.sandbox`; there is no derived fallback name. Its Secret read permission becomes a Role in the sandbox namespace (Secret names are per Project, so `resourceNames` cannot pin them), shipped in the same release as the operator change.

## Consequences
- Capsule and capsule-proxy are no longer used by enzarb at runtime. Whether to keep them as cluster prerequisites is decided together with the future "other namespaces" API access; until then they stay installed but unused.
- Users no longer get kubectl access to a Project namespace (ADR-0002 assumed scoped kubectl through capsule-proxy). Interactive access is the sandbox terminal.
- Per-Project limits come from the sandbox pod's own resources (and a LimitRange for defaults); a namespace ResourceQuota can still cap the total for all sandboxes.
- **Deploy:** the operator, the UI (new checklist) and the chart ship together; the deploy task applies the chart's CRDs explicitly (Helm never upgrades `crds/`). Released sandbox-proxy images keep working (they read the status), so their code updates may follow.
- **Migration (oldie):** workspace data is not migrated. Run the task only after the new operator has fully rolled out (the old one re-adds the finalizer and re-creates Tenants); the task refuses otherwise. A one-off task (`mise run oldie:migrate-0013`) removes the old `enzarb.dev/cleanup` finalizer from existing Projects (otherwise their deletion would hang) and deletes Capsule Tenants labelled `app.kubernetes.io/managed-by=enzarb-operator`. Deleting a Tenant deletes the namespaces Capsule assigned to it, with their volumes; on oldie none exist (the first Project failed before its namespace was created). Projects whose names are 51 to 54 characters long become `InvalidSpec` and must be re-created.

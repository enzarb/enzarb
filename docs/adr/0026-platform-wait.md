# 0026. Platform wait: the engine polls, the step resumes on the same run, nothing times out

Status: Accepted (2026-10-18).

## Context
A step can end with `step_finished.environment` (`disk_full`, `oom`, ...): the code did not fail, the sandbox did. A person should not be needed to restart it. The sandbox already continues the agent session when `step_start` is re-sent for a run that ended with such a failure (#297). What was missing is the engine side: park the task, notice that the condition cleared, and re-send `step_start`. ADRs 0019 (sandbox stats), 0022 (interpreter, ticker) and 0024 (platform facts, no kernel thresholds) constrain the answer.

## Decision
- **Opt-in per step, as data.** A step lists `platform_wait: [{kind, until}]`. `kind` is one of `disk_full`, `oom`, `network`, `load`; `until` is a condition in the closed `When` vocabulary of `checks/*.yaml`, limited to `platform` leaves under `all`/`any`/`not`. A kind not listed behaves as before (the step's `retry`, then the flow's edges on `last.environment.kind`). `toolchain_missing` and `unknown` cannot wait: they may never clear and resuming installs nothing. The kernel ships no thresholds.
- **State.** The task keeps `status: running` and `pending: {step, run_id, attempt}` and gains `platform_wait: {kind, detail, until, waits}` plus a counter `platform_waits` (additive optional fields, so an older engine still decodes the state; a new `Status` variant would not decode). `last` is recorded as for any finish. No edge is followed, no retry is consumed, no attempt is used.
- **Projection.** `waiting_on: external`, `reason: platform_wait`, text "Waiting for the sandbox: <kind> (<detail>)", `needs_you: false`. No new `WaitingOn` value.
- **Wake-up producer: the engine polls, level-triggered.** A ticker pass (`wake_platform_waits`, every tick) reads each waiting task's `until` against the platform facts (the provider of ADR-0024) and, when it holds, inserts the internal `platform_cleared {run_id, wait}` event, deduped on `wake:<task>:<waits>`. An unknown fact keeps the task waiting. Because the pass checks the condition and not an edge, a lost, late or duplicated signal cannot strand a task, and a restart of the engine or the sandbox is covered the same way. Tasks paused by a person are skipped and woken after they resume.
- **Resume.** The interpreter accepts `platform_cleared` only while the task is in the wait of that run with `wait == waits`; anything else is a no-op. It then clears the wait, bumps `platform_waits` and emits `RunStep` with the **same `run_id` and `attempt`** (`resume` = wakes so far, which only distinguishes the job key). The executor re-sends `step_start`; the sandbox continues the session; `step_runs.resumes` counts it. The job goes through the normal queue, so concurrency groups and sandbox holds apply.
- **New platform fact `sandbox.healthy`** (bool): a `sandbox_stats` sample no older than the fact window (10 minutes) exists. It is the generic "the sandbox is reporting again" signal for `oom` and friends. `network` and `load` have no better fact yet.
- **No timeouts, no retry budget, no escalation by age.** A condition that never clears keeps the task in the wait. The wait is *surfaced*: the check leaf `platform_wait: {kind?}` lets a library check (`platform-wait-long`, `kind: platform_failure`) report a long wait (ADR-0024: observation only; it neither wakes nor cancels). A person can still `/cancel` the task or stop the step; nothing else ends the wait. A step that fails again after a wake re-enters the wait with no cap.

- **Library routing (#300).** In the standard library every agent step (`triage`, `plan`, `implement`, `review`, `address`, `ci_fix`, `resolve_conflicts`, `task`, `breakdown`) lists `disk_full` and `oom`. Their environment failures go to the wait before any edge, `set_on_exit` or `max_visits` of the phase node applies, so `review/rounds/human`, `implement/blocked`, a fix round (`fix_rounds`) and `reviewed_sha` are untouched, and the nested `review` phase leaves the task `running`. `network` and `load` are not listed: `sandbox.healthy` would clear at once and the step would fail and re-enter the wait with no cap (gaps.md #22), so they keep their edges, like `toolchain_missing` and `unknown`. Non-agent steps (`checks`, `prepare`, `context`) do not wait. A failure with no `environment` keeps its routes. `tests/library.rs` covers both.

## Alternatives rejected
- **A push event from the sandbox or pruner.** It needs a new cross-component contract (a proto frame or an API), is edge-triggered so a lost event strands the task, and would still need a catch-up poll. It remains a possible latency optimisation on top of the poll; the poll stays the source of truth.
- **A new `Status::PlatformWait` variant.** An engine of the previous release could not decode the state during a rolling deploy.
- **Default-on waiting for `disk_full`/`oom`.** It would change existing workflows; opting in keeps them as they are. The stdlib agent steps opt in.
- **A wait deadline that pauses the task.** The issue forbids timeouts and escalation by age.

## Agent-reported environment (advisory)
`review` and `implement` results may carry an optional `environment` object (`{kind?, detail}`). It is advisory and never routes: only `step_finished.environment` decides edges, waits and retries. When the sandbox also detected a failure that the step waits out, the agent's `detail` (truncated to 500 characters, shown as text only) is appended to the wait detail as `<sandbox detail>; agent: <agent detail>`.

## Consequences
Wake latency is the stats poll interval (ADR-0019) plus the ticker interval; nothing here is time-critical. Flapping (wake, refill, fail again) loops by design; each cycle produces events, so the `idle_for` of `platform-wait-long` restarts, and a check keyed on the wait's age instead is future work. Memory, chart-deploy and workflow-run facts stay unknown (ADR-0024).

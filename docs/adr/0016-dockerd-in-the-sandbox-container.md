# 0016. dockerd in the sandbox container, supervised by sandbox-init

Supersedes the sidecar part of [ADR-0012](0012-docker-in-sandbox.md). Everything else in ADR-0012 stands: Docker is always on, isolation is mandatory and cluster-admin owned, gVisor is the runtime, the agent permission policy.

## Context
ADR-0012 ran `dockerd` as a sidecar and shared `/var/run/docker/docker.sock` through an `emptyDir`. Under `runtimeClassName: gvisor` that does not work (issue #92): a plain `emptyDir` shared between two containers is gofer-backed, and the gofer carries regular files but not Unix domain sockets across containers. The sandbox saw the directory but no `docker.sock`. A sidecar also has no `/workspace`, so `docker run -v /workspace/repo:/src` and `docker compose` bind mounts resolved against the wrong filesystem.

## Decision
- **dockerd runs in the `sandbox` container.** gVisor's documented Docker setups ([Docker in gVisor](https://gvisor.dev/docs/tutorials/docker-in-gvisor/), [Docker in a GKE sandbox](https://gvisor.dev/docs/tutorials/docker-in-gke-sandbox/)) do the same. The pod has one container, no `dockerd` sidecar and no `docker-sock` volume. The `docker-data` volume (PVC `sb-<name>-docker`, `/var/lib/docker`) stays, so image caches survive.
- **sandbox-init supervises it** (`sandbox-container/src/dockerd.rs`).
  - Socket `unix:///var/run/docker.sock` (`DOCKER_HOST` in the image and set by the operator), group 1000, mode 0660. No TCP listener.
  - Flags: `--group=1000 --data-root=/var/lib/docker --exec-root=/var/run/dockerd` plus the runtime profile's `dockerdArgs`, which the operator passes as `ENZARB_DOCKERD_ARGS` (gVisor: `--iptables=false --ip6tables=false --storage-driver=vfs --feature=containerd-snapshotter=false`).
  - Restart on exit with exponential backoff (1 s to 30 s, reset after 60 s of stable running). State `starting | running | failed | stopped | disabled` is logged and reported in `GET /healthz` as JSON (`{"status":"ok","dockerd":{"state":"running"}}`). The response stays HTTP 200: the readiness probe never depends on Docker.
  - If dockerd cannot start (or is not installed), agents and chats still work; Docker is unavailable and the failure is logged. `ENZARB_DOCKERD=off` disables the supervisor.
  - On SIGTERM it stops after the chats and before the blanket signal to the other children: SIGTERM to dockerd, wait the grace period, then SIGKILL. dockerd stops its containers and releases its data root before the drain completes.
- **sandbox-init is root, everything else is uid 1000.** The operator sets the `sandbox` container's `securityContext` from the runtime profile (gVisor: not privileged, `runAsUser: 0`, `runAsNonRoot: false`, `allowPrivilegeEscalation: true`, `drop: [ALL]` plus the capability set gVisor documents for Docker). The pod-level `runAsUser`, `runAsGroup`, `fsGroup` and `fsGroupChangePolicy` stay, so the workspace and the auth token keep their ownership. Every process sandbox-init spawns other than dockerd (agents, git, `mise`, PTY shells) goes through one helper (`src/privs.rs`): `setgroups([1000])`, `setresgid`, `setresuid` to 1000, `PR_SET_NO_NEW_PRIVS`, and `HOME`/`USER`/`LOGNAME` set. PTYs, which `portable-pty` cannot hook, are started through `sandbox-init --exec-as-sandbox-user`. A unit test fails if a new spawn site bypasses the helper. Files sandbox-init creates under `/workspace` are chowned to 1000. sandbox-init stays non-dumpable.
  - Alternative rejected: a small root launcher that starts dockerd and then execs sandbox-init as 1000. No supervisor would remain in pid 1.
  - Rootless Docker and userns-remap: not pursued (undocumented in gVisor, user-namespace support is partial, little gain inside the sandbox).
- **Inner containers default to host networking.** With `--iptables=false` the default bridge has no NAT, so containers would have no egress. The image's `docker` is a wrapper (`/usr/local/bin/docker`, real client in `/usr/local/libexec/docker/docker`) that adds `--network=host` to `run`, `create` and `build` (also `container run|create`, `buildx build`, `builder build`) before the caller's arguments, so an explicit `--network` wins. `ENZARB_DOCKER_NETWORK=default` turns it off. "Host" is the sandbox container's gVisor network namespace, not the node's; the per-Project egress NetworkPolicy (DNS and 443) still applies. `-p` does not publish ports; compose services need `network_mode: host`. (A daemon-wide `daemon.json` default was not used: no dockerd setting for the default container network mode was found, and it would not cover `docker build`.)
- **Ownership.** Inner containers run as root by default, so files they write to a bind mount are root-owned. Use `--user 1000:1000` (the policy allows it). The policy cannot add flags, so this stays a documented known limitation.
- **Resources.** dockerd, containerd and inner containers share the `sandbox` container's CPU and memory limits. The `--docker-image` and `--docker-cpu-*`/`--docker-memory-*` operator flags (and `operator.docker.image` / `operator.docker.resources` in the chart) are removed.
- **Image.** The static Docker bundle (`docker`, `dockerd`, `containerd`, `containerd-shim-runc-v2`, `runc`, `docker-init`, `docker-proxy`), sha256-pinned per arch, plus the buildx and compose plugins. The image has no `USER` line: pid 1 starts as root under the operator's override.

## Consequences
- **Security posture.** The sandbox container's pid 1 is root, with `SYS_ADMIN` and `NET_ADMIN` that exist only in gVisor's sandbox kernel. An agent runs as uid 1000 with no-new-privs; a gVisor escape, or a spawn site that skips the helper, would give it root. The helper is the only spawn path (tested).
- **Rollout.** The pod shape changes (new mount, new env, new container security context, no sidecar), so every existing sandbox drains and rolls once through the existing drain-first path in the operator.
- **Operator flags.** Removing the `--docker-*` image and resource flags is a breaking change for anyone who passes them; the chart is updated in the same change, and unknown environment variables are ignored by older charts.
- **Failure isolation.** A heavy build can OOM the whole sandbox container, agents included. Raising the default limits is a follow-up if needed.
- **Storage.** `vfs` on the PVC is slow and large. If it is unusable for real builds, a tmpfs data root (gVisor's other v29 option) is the follow-up.

## Addendum: automatic pruning (issue #120)
Nothing deleted images, build cache or stopped containers from the `docker-data` volume, and `vfs` copies every layer: a sandbox filled its 50G PVC in about 3.7 days. sandbox-init now prunes (`sandbox-container/src/docker_prune.rs`).
- **Policy.** `docker container prune -f`, `image prune -af`, `builder prune -af`, `volume prune -f`, in that order, run as uid 1000 through the reaper. *Aged* mode adds `--filter until=<age>` (`ENZARB_DOCKER_PRUNE_AGE`, default 24h) to the image and builder steps; it runs once dockerd is `running` and when the last active run or chat ends. *Aggressive* mode omits the filter; it runs when the 5-minute free-space check finds the data root under `ENZARB_DOCKER_PRUNE_MIN_FREE` (default 15%). `ENZARB_DOCKER_PRUNE=off` disables pruning. The chart exposes the three settings as `operator.docker.prune.*`; the operator passes them to sandboxes.
- **Never interrupt a build.** The docker CLI already refuses to remove running containers and the images and volumes they use. A build in flight is invisible to it, so an `ActivityGate` counts active runs and chats (held in `agent.rs` and `chat.rs`). Image and builder pruning only runs while the gate is idle; an aged prune is skipped entirely when it is not, and a low-disk prune does only the container and volume steps. This is coarse on purpose: finer tracking of docker child processes is a possible follow-up.
- **Serialised and best-effort.** One prune at a time (a second caller skips rather than queues). A failing step is logged and the sequence continues; a missing `docker` skips the prune. Pruning never fails a run, a chat or `/healthz`.
- **Visibility.** Bytes freed are the free-space delta of the data root (`statvfs`) around the sequence, logged on every prune (not parsed from docker's output, which varies by command). `/healthz` adds `docker_disk` (used/free bytes, `low_disk`) and `docker_prune` (`enabled`, `last`) without changing `dockerd`. `low_disk` stays true while under the threshold, even after pruning.
- **Rejected.** `docker system prune` (no per-object filters), pruning from the agent's shell or the policy (the agent could skip it), parsing `Total reclaimed space`.

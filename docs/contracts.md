# Cross-repo contracts

Interfaces that more than one repo depends on. Implementations must match this document. If a change needs a different shape, update this file in the same change (top-level `enzarb` repo) and say so in the PR.

## 1. Rust library dependencies

```toml
enzarb-proto       = { git = "ssh://git@github.com/enzarb/enzarb-proto.git", branch = "main" }
enzarb-crds        = { git = "ssh://git@github.com/enzarb/enzarb-sandbox-operator.git", branch = "main" }
enzarb-connector   = { git = "ssh://git@github.com/enzarb/enzarb-connectors.git", branch = "main" }
enzarb-connector-github = { git = "ssh://git@github.com/enzarb/enzarb-connectors.git", branch = "main" }
```
- Libraries are merged to `main` before dependents use them; `Cargo.lock` pins the commit. Pick up changes with `cargo update -p <crate>`. Never commit a `[patch]` to a local path.
- Crate paths:
  - `enzarb-proto/crates/enzarb-proto`
  - `enzarb-sandbox-operator/crates/enzarb-crds`
  - `enzarb-connectors/crates/connector`
  - `enzarb-connectors/crates/connector-github`
- TS: `@enzarb/proto` is published to GitHub Packages npm (`npm.pkg.github.com`) on merge to main (enzarb-proto issue for publishing). `enzarb-ui` installs it via `.npmrc` `@enzarb:registry=https://npm.pkg.github.com`; CI authenticates with `GITHUB_TOKEN` after the package grants the repo read access.

Shared choices across the Rust repos:
- tokio, axum 0.8, tracing + tracing-subscriber (JSON logs), serde, thiserror/anyhow;
- sqlx (postgres, runtime-tokio, tls-rustls), kube + k8s-openapi (latest k8s feature), reqwest (rustls), jsonwebtoken;
- toolchain: stable, pinned in `rust-toolchain.toml` in each repo, edition 2024.

## 2. `Project` CRD (`enzarb.dev/v1alpha1`, **cluster-scoped**)

Types are in the `enzarb-crds` crate; the CRD YAML is generated by `cargo run -p enzarb-crds --bin crdgen`.

```yaml
apiVersion: enzarb.dev/v1alpha1
kind: Project
metadata: { name: enzarb }            # DNS label, max 50 chars ("sb-<name>-workspace" ≤ 63)
spec:
  owner: ruckc                         # owner id (GitHub login of the creator)
  displayName: enzarb
  repositories:
    - url: https://github.com/enzarb/enzarb-ui    # canonical https URL
      connector: github
      defaultBranch: main
  runMode: worktree                    # worktree | fresh (fresh is post-MVP)
  triggers: { issues: true, changeRequests: true, mentions: true }
  sandbox:
    image: ""                          # empty = operator default (--sandbox-image)
    storage: 20Gi
    resources: {}                      # core/v1 ResourceRequirements
status:
  observedGeneration: 3
  namespace: enzarb-sandboxes          # the shared sandbox namespace (ADR-0013)
  sandbox:
    name: sb-enzarb                    # Sandbox CR name in that namespace: "sb-<project>"
    endpoint: ws://sb-enzarb.enzarb-sandboxes.svc:7070/v1/mux
    authSecretRef: { name: sb-enzarb-auth, key: token }   # in status.namespace
  conditions:                          # metav1.Condition, ordered for the UI checklist
    - type: ResourcesReady             # auth Secret, workspace + docker PVCs, NetworkPolicy
    - type: SandboxReady
    - type: Ready
  claudeCredentialReady: true          # presence of the owner's Secret enzarb-claude-<owner>; never the value
```

Conditions: a failed step is `status: False` with a `reason` ending in `Failed`, `Failure` or `Error` (e.g. `NotOwnedError`: an object with the Project's name exists but has no owner), or the named terminal reason `InvalidSpec` (reported on `ResourcesReady`, for an invalid Project name and for a repository that another Project already owns, see "One Project per repository" below). Any other `False` reason is shown as in progress (e.g. `Terminating`: a deleted Project's objects with the same name are still being removed).

Objects per Project (ADR-0013), all in the shared namespace and labelled `enzarb.dev/project=<name>`: Sandbox `sb-<name>` (its pod and headless Service share the name; the Service is owned by the Sandbox), Secret `sb-<name>-auth`, PVCs `sb-<name>-workspace` and `sb-<name>-docker`, NetworkPolicy `sb-<name>`, each with a controller ownerReference to the Project. Not per Project: the owner's Claude token Secret `enzarb-claude-<spec.owner>` (labelled `enzarb.dev/claude-credential=<owner>`, no ownerReference, never deleted with a Project); `spec.owner` is immutable. Names are at most 50 characters, enforced by a CEL rule in the CRD, the operator and the UI. Sandbox pods run as ServiceAccount `enzarb-sandbox` with no token and no RBAC: **no Kubernetes API access**; any future access is limited to other namespaces. Consumers find the sandbox only through `status.namespace` and `status.sandbox` (no derived fallback).

Defaults: `runMode: worktree`, all `triggers` true, `sandbox.storage: 20Gi`. Helpers in `enzarb-crds`: per-Project object names (`sandbox_name()`, `auth_secret_name()`, `workspace_pvc_name()`, `docker_pvc_name()`), `matches_repo()`, `RepoKey::from_url` / `RepoKey::from_connector_url` (github.com only for now; lowercases).

Resources and pod-shape changes: `spec.sandbox.cpu` (integer 1-64) and `spec.sandbox.memory` (`<int>Mi|Gi`, 512Mi-256Gi) set the sandbox container limits; the operator derives requests at 25% (floors 100m / 256Mi), and explicit `spec.sandbox.resources` win per key. Unset injects nothing. Any change to the desired pod shape (image, `ENZARB_*` env incl. `spec.maxRuns`, sandbox and dockerd resources, runtime class, mounts) is **queued, not applied**: the operator publishes `status.pendingChange {generation, since, reason}` and the informational condition `SandboxChangePending` (replaces `SandboxImageRoll`; no effect on `Ready`) and leaves the pod alone. After workflows has drained the sandbox it sets the Project annotation `enzarb.dev/drained-generation` to the `generation` it read (needs `patch` on `projects`); only an exact match releases the operator to delete the pod (never the Sandbox or PVCs). A newer spec change bumps `generation`, so an older ack no longer applies. Without an ack the operator applies the change after `--sandbox-roll-drain-timeout` (default 2h) from `since`. `pendingChange` is removed once the recreated pod matches. Storage growth is not queued (the PVC expands in place).

Repo key: a repository's **repo key** is `<connector>:<owner>/<repo>`, e.g. `github:enzarb/enzarb-ui`, always lowercase. Workflows and connectors route events by matching an event's repo key against the Projects' `spec.repositories`.

One Project per repository: a repo key (`RepoKey::from_connector_url`, compared case-insensitively) belongs to at most one Project. When several Projects list it, the oldest by `(metadata.creationTimestamp, name)` wins; `name` breaks timestamp ties and is unique because the CRD is cluster-scoped. Every other Project has `ResourcesReady=False` with the terminal reason `InvalidSpec`, like an invalid name; its message names the repository only, never the winning Project. Losing Projects must receive no events: workflows and connectors must route a repository's events only to the winner. That is the contract those repos have to meet, not behaviour that exists today. The operator side is tracked in enzarb-sandbox-operator#19 (pending); the routing work is tracked in the follow-up issues linked from there.

## 3. sandbox-init

**Mux endpoint:** `ws://<pod>:7070/v1/mux`. Clients must send `Authorization: Bearer <token>`. The token is the `token` key of the Secret named in `status.sandbox.authSecretRef` (`sb-<project>-auth`) in `status.namespace`; the operator generates it, and it is mounted in the sandbox at `/var/run/enzarb/auth/token`.
- Allowed clients: `sandbox-proxy` and the workflows executor.
- Health: `GET :7070/healthz`.

**Docker (ADR-0012):** always on. The operator sets the pod `runtimeClassName` (`gvisor`) cluster-wide via `--sandbox-runtime-class`, and adds the dockerd sidecar. `DOCKER_HOST=unix:///var/run/docker/docker.sock` (shared emptyDir with the `dockerd` sidecar). The image ships the `docker` CLI plus the buildx and compose plugins.

**PTY channels:** CLOSE reason is `exit:<code>` or `signal:<n>`. A client half-close leaves the process running.

**Config (env):**
- Core: `ENZARB_LISTEN` (default `0.0.0.0:7070`), `ENZARB_AUTH_TOKEN_FILE`, `ENZARB_WORKSPACE` (`/workspace`), `ENZARB_SHELL`, `ENZARB_GRACE_SECS` (25; the pod's `terminationGracePeriodSeconds` must be larger).
- Runs: `ENZARB_MAX_RUNS` (2), `ENZARB_RUN_TIMEOUT_SECS` (3600), `ENZARB_CALLBACK_BACKOFF_MS`, `ENZARB_GIT_NAME`, `ENZARB_GIT_EMAIL`, `ENZARB_CLAUDE_TOKEN_FILE`.
- Agent: `ENZARB_ACP_AGENT_BIN` (default `claude-agent-acp`), `ENZARB_CANCEL_GRACE_SECS` (10), `ENZARB_PERMISSION_POLICY` (YAML/JSON file; built-in default when unset).
- Chat (ADR-0014; sandbox-init config only, no Project spec field): `ENZARB_MAX_CHATS` (1; `0` disables chat and removes `acp` from `welcome.features`; chats never use `ENZARB_MAX_RUNS` slots), `ENZARB_CHAT_IDLE_SECS` (1800), `ENZARB_CHAT_MAX_SECS` (28800), `ENZARB_CHAT_RETENTION_DAYS` (7).
- Chat permission mode (ADR-0014 amendment 2026-10-12 (2); sandbox-init config only): `ENZARB_CHAT_PERMISSION_MODE` (`bypassPermissions` default | `default` | `plan`; other values fail startup; defaults to `default` when bypass is not allowed) and `ENZARB_CHAT_ALLOW_BYPASS` (true; `false` makes bypass unavailable, and `false` with an explicit bypass mode fails startup). Browser-bound `_enzarb/mode {sessionId, modeId, bypassAllowed}` is sent after session establishment and after each successful `session/set_mode`. The `session/set_mode` allowlist is {`bypassPermissions` (only while allowed), `default`, `plan`}. In bypass the agent sends no `session/request_permission` for ordinary tool calls, so `Policy::hard_deny` applies only in `default`/`plan`. Agent jobs are unchanged.

**Agent runs (ACP, ADR-0011):**
- sandbox-init is an ACP client of `@agentclientprotocol/claude-agent-acp` (pinned 0.88.0), one agent process per run, with cwd set to the worktree and `CLAUDE_CODE_OAUTH_TOKEN` in its environment.
- **Protocol steps:** `initialize`, then `session/new` (mode `default`), then `session/prompt`.
- **Permissions:** every `session/request_permission` is answered by the policy with `allow_once` or `reject_once`, never persistent options.
  - Edits are limited to the worktree.
  - Reads (Read/Grep/Glob and read-only shell utilities) may also reach the Project's other repo checkouts and worktrees (`/workspace/repos`, `/workspace/worktrees`). Writes, `cd` and docker bind mounts stay inside the run's own worktree (enzarb-sandbox-container#27).
  - `git -C <dir>` is allowed only for a `<dir>` in the read roots and a read-only subcommand (`status`, `log`, `show`, `diff`, `rev-parse`, `ls-files`, `ls-tree`, `grep`, `blame`, `branch --list`, `cat-file`).
  - Secrets are unreadable under any root: `.enzarb` (including `claude-token`), `/run/enzarb/claude`, `.git-credentials`, `.gitconfig`, `.netrc`, git credential helper config.
  - Commands must match the allowlist; shell metacharacters and expansions are denied.
  - Network fetch is denied unless the host is allowlisted.
- **Summary:** the verbatim agent text of the turn. `exit_code` is 0 on `end_turn`, the agent's code on a crash, and null when cancelled or timed out.
- **Cancel:** `session/cancel`, then a grace period, then the process group is killed.

**Interactive chat (ACP, ADR-0014; [design](design/chat-tab.md)):**
- One `acp` mux channel is one `claude-agent-acp` child, in its own process group. DATA_BIN carries newline-delimited JSON-RPC (max line 4 MiB). sandbox-init is a filtering relay: it forces `clientCapabilities` to none, `cwd` to the chat worktree and `mcpServers` to `[]`, allows only `initialize`, `session/new`, `session/load` (registered sessions only), `session/prompt`, `session/cancel` and `session/set_mode` (`default` or `plan`), and redacts the Claude token.
- **Permissions:** `Policy::hard_deny` rejects (`reject_once`) secrets, `.enzarb`, the mux auth token, edits outside the chat worktree, `git push` and non-allowlisted fetches, and notifies the browser with `_enzarb/permission_denied`. Every other request goes to the user; only `allow_once`, `reject_once` or `cancelled` answers are accepted, and anything else becomes `reject_once`. No path auto-approves.
- **Environment:** the Claude token only. A chat never receives `clone_token`, `deps_token` or `npm_token`, so it cannot push or install private packages.
- **Limits:** at `ENZARB_MAX_CHATS` a new open closes the existing chat with `superseded`; 1 `acp` channel per socket; prompts up to 256 KiB. Chat does not block drain.
- **CLOSE reasons on an `acp` channel:** `idle`, `superseded`, `shutdown` (sandbox-init got SIGTERM), `limit` (hard lifetime or line cap), `exit:<n>`, `signal:<n>`.

**Image build:** `docker buildx build --secret id=proto_key,src=<key> --load .` (private enzarb-proto dependency). The minimal runtime image (ADR-0012, enzarb-sandbox-container#16) contains:
- sandbox-init;
- node 24 + claude-agent-acp + the glibc `claude` binary;
- mise;
- build-essential, pkg-config, libssl-dev;
- git, ca-certificates, openssh-client.

Plus curl (mise's Rust backend needs it for rustup) and the docker CLI with the buildx and compose plugins (29.8.2, matching the dockerd sidecar). No Rust, npm or extra CLI tools.

**Toolchains (mise, per project, persisted on the PVC):**
- `MISE_DATA_DIR=/workspace/.toolchains/mise`, `MISE_CACHE_DIR=/workspace/.toolchains/cache`, `CARGO_HOME=/workspace/.toolchains/cargo`, `RUSTUP_HOME=/workspace/.toolchains/rustup`.
- `MISE_TRUSTED_CONFIG_PATHS=/workspace`, `MISE_YES=1`, `MISE_IDIOMATIC_VERSION_FILE_ENABLE_TOOLS=rust`.
- `PATH` includes the mise shims, so a repo's `mise.toml` or `rust-toolchain.toml` determines its tools.

**Transcript records** (`transcript.jsonl`, also streamed on `log_channel`). Each has `ts` and `kind`:
- `state {state, branch?}`
- `worktree {path, branch, start, base}`
- `log {source: git|acp, line}`
- `acp {event: initialized|session|cancel, …}`
- `update {session_id, update}` (the raw ACP `session/update`)
- `permission {tool_call_id, tool_kind, title, input, decision, rule, reason, option_id}`
- `agent_result {stop_reason, text}`
- `finished {outcome, exit_code, head_sha, pushed}`

Secrets are redacted from all records.

**Filesystem (on the PVC):**
- `/workspace`: repos and worktrees.
- `/workspace/.toolchains/`: mise data and cache, cargo, rustup.
- `/workspace/repos/<slug>-<hash>/`: one clone per repo URL.
- `/workspace/worktrees/run-<run_id>/`: the run's worktree. It starts from `origin/<branch>` if that exists, otherwise from `base_ref`. It is deleted when the run ends (the branch stays in the clone); at sandbox-init startup and before each run, `run-*` dirs of no active run are pruned.
- `/workspace/.enzarb/runs/<run_id>/`: `state.json`, `request.json` (0600, clone token blanked), `transcript.jsonl`, and `callback.json` while a callback is pending.
- `/workspace/worktrees/chat-<chat_id>/`: a chat's worktree (`chat_id` is 16 random hex chars), detached at `origin/<default branch>` of the chosen clone; commits go on the local branch `enzarb/chat-<chat_id>`. `run-*` pruning never touches it; a sweep removes chat worktrees with no live channel and no activity for `ENZARB_CHAT_RETENTION_DAYS`.
- `/workspace/.enzarb/chats/<chat_id>/`: `meta.json` (`acp_session_id`, `repo`, `worktree`, `created`, `last_active`) and `transcript.jsonl` (0600; same record kinds as runs, plus `prompt`).
- `/workspace/.enzarb/chat-home/.claude`: `CLAUDE_CONFIG_DIR` for chat agents, so `session/load` survives pod restarts.
- `/workspace/.enzarb/claude-token`: mode 0600. Legacy per-Project token, read only as a fallback; sandbox-init promotes it to the user Secret via `credential_captured` when the user has none, then deletes it once `/run/enzarb/claude/token` exists.

## 4. enzarb-proto messages

The wire format (frame layout, flow control) is defined in `enzarb-proto/docs/protocol.md`. Frame types: `CTRL, DATA_BIN, DATA_JSON, WINDOW, CLOSE`.

CTRL payloads are JSON objects tagged by `"type"` and use channel 0:

| Message | Direction | Fields |
|---|---|---|
| `hello` | client → server | `versions: [1]`, `client: "ui" \| "proxy" \| "executor"` |
| `welcome` | server → client | `version`, `features?: [string]` (optional; `"acp"` when chat is enabled; absent means none) |
| `open` | client → server | `channel`, `kind: "pty" \| "acp"`, `cols`, `rows`, `command?: [..]`, `repo?`, `resume?` (see below) |
| `opened` / `open_error` | server → client | `channel` / `channel, message, code?` |
| `resize` | client → server | `channel`, `cols`, `rows` |
| `run_start` | client → server | see below |
| `run_accepted` | server → client | `run_id`, `state`, `existing: bool` |
| `run_status` → `run_state` | both | `run_id` → `run_id, state, exit_code?, summary?` |
| `run_cancel` | client → server | `run_id` |
| `credential_captured` | server → client | `kind: "claude_oauth"`, `token?` (the captured token; **proxy-only**: the proxy consumes the frame, stores the token and never forwards it, and it is never logged) |
| `credential_status` | client → server | (none); browsers may send it |
| `credential_state` | server → client | `kind: "claude_oauth"`, `configured: bool`, `scope?: "user"` (the Claude token is per user, ADR-0004 amendment 2026-10-13) |
| `credential_clear` | client → server | `kind: "claude_oauth"`; browsers may send it (on the proxy's allowlist). The proxy handles it locally by deleting the owner's Secret and answers `credential_state{configured:false, scope:"user"}`; it is not forwarded to the sandbox |
| `error` | both | `code`, `message`, `run_id?`, `channel?` (a `run_id` routes the error to that run's pending request) |

**Claude token (per user, ADR-0004 amendment 2026-10-13):** Secret `enzarb-claude-<owner>` (key `token`, label `enzarb.dev/claude-credential=<owner>`) in the shared sandbox namespace, written and deleted only by the proxy, with the name derived from the authenticated `spec.owner`. The operator mounts it into each owned sandbox as an optional read-only volume at `/run/enzarb/claude/`, so `ENZARB_CLAUDE_TOKEN_FILE` defaults to `/run/enzarb/claude/token`. sandbox-init reads it per run and chat open, falling back to the legacy `/workspace/.enzarb/claude-token`; a missing token answers `no_credential`, which workflows reports as a non-retried "owner has no Claude credential" failure. Changes reach a running sandbox after the kubelet's Secret propagation (about a minute). The Secret name is never taken from frame content, which is the compensating control for the proxy's name-unrestricted `create` (section 7). `app_api.project_settings.claude_token_configured` is a deprecated alias, derived from `status.claudeCredentialReady` of the Project's owner; new code reads the status field.

**`acp` channels (ADR-0014; additive, protocol version stays 1):**
- `kind: "acp"` opens a byte stream of newline-delimited JSON-RPC (ACP) in DATA_BIN; messages may span frames. `cols`/`rows` are ignored (clients send `0`). `repo` (optional) names a Project repo URL that must already be cloned; `resume` (optional) is the ACP session id, informational only.
- **`welcome.features`:** the sandbox sends `["acp"]` when `ENZARB_MAX_CHATS > 0`. The proxy answers the browser's `hello` itself and forwards the sandbox's features intersected with those it can guard. Decoders ignore unknown fields.
- **Compatibility rule:** a sender must not send `open{kind:"acp"}` before seeing `"acp"` in `welcome.features`. A proxy that cannot decode a frame closes the socket with 1008, so an `acp` open to an old proxy would kill the connection.
- **`open_error.code`** (optional): `chat_disabled`, `chat_limit`, `no_credential`, `repo_not_cloned`, `unsupported_kind`. Clients must tolerate other values. An unknown `kind` decodes (Rust `ChannelKind::Unknown`) and yields `unsupported_kind`.
- **CLOSE reasons** on an `acp` channel: `idle`, `superseded`, `shutdown`, `limit`, `exit:<n>`, `signal:<n>`. Clients must tolerate other text.

`run_start` fields:

```json
{ "type": "run_start", "run_id": "job-123",
  "repo_url": "https://github.com/enzarb/enzarb-ui", "base_ref": "main",
  "branch": "enzarb/issue-42", "push": true,
  "clone_token": "<short-lived installation token>",
  "prompt": "…", "timeout_secs": 3600,
  "callback_url": "http://enzarb-workflows-executor.enzarb.svc:8081/v1/runs/job-123/finished",
  "callback_token": "<hex HMAC-SHA256(executor secret, run_id)>",
  "log_channel": null,
  "deps_token": "<optional, omitted when absent>",
  "npm_token": "<optional, omitted when absent>" }
```
- **`npm_token`** (optional, additive): a **long-lived** token with `read:packages`, for `npm ci` of private `@enzarb/*` packages on npm.pkg.github.com. GitHub App installation tokens cannot read org packages even with `packages: read` (E403 "Permission installation not allowed to Read organization package"), so `deps_token` cannot serve that role. The workflows executor reads it from `ENZARB_NPM_TOKEN` / `ENZARB_NPM_TOKEN_FILE` (in the chart: Secret `enzarb-updater-registry`, key `registry-token`) and sets it on implement, address-comments, resolve-conflicts and review runs only; it is never stored in `jobs.input`. sandbox-init exposes it to the agent process only, as `NODE_AUTH_TOKEN` (it takes precedence over the `deps_token` fallback; `ENZARB_DEPS_TOKEN` keeps feeding cargo/git), redacts it (and its basic-auth base64 forms) from transcripts, summaries and callbacks, and never writes it to `request.json`, state, callback files or an `.npmrc`. Debug output of `RunStart` redacts it. Absent means `NODE_AUTH_TOKEN` falls back to `deps_token`.
- **Wire details** (`enzarb-proto/docs/protocol.md` and the `enzarb_proto::Ctrl` enum are the source of truth):
  - 10-byte big-endian header: type, flags (0), channel u32, length u32. Max payload 1 MiB, one frame per websocket binary message.
  - 256 KiB initial window per channel and direction. `CLOSE` is a half-close.
  - Optional fields are omitted when absent; `null` is accepted on decode.
- **`run_state`** is sent in reply to `run_status` and also pushed whenever a run changes state.
- **`log_channel`:** a non-null value is a channel the client chooses. `run_accepted` implicitly opens it, and the server streams transcript lines on it as `DATA_JSON`.
- **`RunFinished`** (`enzarb_proto::RunFinished`) is the callback's HTTP body, not a CTRL message. `exit_code` is optional because cancelled runs may have none.
- **Idempotent:** a repeated `run_id` returns the existing run.
- **States:** `queued | running | succeeded | failed | cancelled`.
- **What the run does:**
  1. ensures the repo clone and creates worktree `run-<run_id>` on `branch` from `base_ref`;
  2. runs the ACP agent with the prompt (see Agent runs above);
  3. if `push`, pushes `branch` with `clone_token`.

**Run finished callback:**
- **Request:** `POST callback_url` with `Authorization: Bearer <callback_token>`. sandbox-init retries with backoff until it gets a 2xx.
  ```json
  { "run_id": "job-123", "outcome": "succeeded|failed|cancelled", "exit_code": 0,
    "summary": "<claude result text>", "branch": "enzarb/issue-42",
    "head_sha": "abc…", "pushed": true }
  ```
- **Fallback:** the executor also polls `run_status` for jobs past their deadline.
- **Comments:** the executor posts comments to GitHub. Sandboxes never get a GitHub token other than the repo-scoped `clone_token`.

## 5. Normalized events (`enzarb-connector` crate → `workflows.events.payload`)

```json
{ "specversion": "1.0", "source": "github", "id": "<delivery id>", "type": "CommentAdded",
  "subject": "github:enzarb/enzarb-ui#42", "time": "2026-10-08T12:00:00Z",
  "data": {
    "repo": "github:enzarb/enzarb-ui",
    "actor": { "login": "ruckc", "id": 42, "is_bot": false },
    "item": { "kind": "issue|change_request", "number": 42, "url": "…", "title": "…", "body": "…",
              "author": "ruckc", "head_ref": null, "base_ref": null, "head_sha": null },
    "comment": { "id": 987, "body": "…", "url": "…" }
  } }
```
- **Rust types:** `enzarb_connector::{Event, EventData, EventType}` are the source of truth for field shapes. `review.state` is a free string.
- **`type`:** one of `WorkItemOpened, CommentAdded, Mentioned, ApprovalGranted, ChangeRequestOpened, ChangeRequestUpdated, ReviewSubmitted, WorkItemClosed, CiStatusChanged`.
  - `WorkItemClosed` carries `data.merged: bool`.
  - `ReviewSubmitted` carries `data.review: {id, state, body}`.
  - `CiStatusChanged` carries the optional `data.ci`, **one per check run, check suite or commit status** (not an aggregate): `{head_sha, state: "success" | "failure" | "pending", context?, url?}` (`state` is lowercase). Additive: consumers that ignore `CiStatusChanged` or `data.ci` are unaffected. Aggregation into one CI verdict happens in `get_merge_readiness` (below); the rule is in enzarb-connectors `docs/connectors.md`.
- **`subject`:** the work item key, `<repo key>#<number>`. Issues and PRs share GitHub's number space, so `#` is used for both.
- **`ApprovalGranted`:** a `/approve` comment on its own line, or the label `enzarb:approved`.
- **`Mentioned`:** `@<bot handle>` in a comment or issue body (handle configurable, default `enzarb`).
- **Bot actor:** events whose actor is the bot itself are dropped by the receiver.
- **Derived events:** one delivery can produce several events. The primary event keeps the delivery id; derived ones get `<delivery>#mentioned` and `<delivery>#approved`, so the dedupe key is `github:<event id>`.
- **Mentions and approval on PRs:** `Mentioned` also fires from a PR body when the PR is opened, and the approval label works on PRs as well as issues.
- **API:** `enzarb_connector_github::normalize(...)` returns `Normalized::Events{events}` or `Normalized::Installation{change}`.
- **Merge methods** (additions to the `Connector` trait, see [connectors.md](connectors.md#outbound-the-connector-trait)). Squash is the only merge method.
  - `merge_change_request(item, number, expected_head_sha, commit_title, commit_body?, idempotency_key) -> MergeOutcome`. The merge is pinned to `expected_head_sha`. `MergeOutcome` is `merged{sha} | already_merged{sha?} | head_moved | not_mergeable{reason}`.
  - `get_merge_readiness(item, number) -> MergeReadiness{head_sha, mergeable: Option<bool>, mergeable_state, ci, ...}`. It aggregates CI (all checks and statuses on the head; no CI counts as passing). The remaining fields and the `mergeable_state` values are defined by `enzarb_connector::MergeReadiness`.

## 6. `workflows_api` (Postgres, owned by enzarb-workflows)

```sql
workflows_api.ingest_event(p_source text, p_dedupe_key text, p_work_item_key text,
                           p_type text, p_payload jsonb) RETURNS bigint   -- NULL if duplicate
workflows_api.submit_action(p_work_item_id bigint, p_actor jsonb, p_action text,
                            p_payload jsonb) RETURNS bigint               -- actions: approve | cancel | retry | merge
-- views
workflows_api.work_item_v(id, key, project, workflow, state, state_data, created_at, updated_at)
workflows_api.transition_v(id, work_item_id, from_state, to_state, event_type, at)
workflows_api.job_v(id, work_item_id, kind, status, attempt, created_at, updated_at, output)
```
- Both functions are `SECURITY DEFINER`.
- Connectors use dedupe key `github:<event id>`; the UI uses `ui:<uuid>`. Events the engine itself generates use source `engine` (`handoff:<id>`, `timer:…`, `job:<id>:<attempt>`).
- `transitions.work_item_id` is nullable: events that are ignored (no Project, no workflow) get a `to_state='ignored'` row with no work item. `transitions.note` records rejections.
- `work_items.state_data` carries `title` and `url` for display. For `change_request` items it may also carry (additive):
  - `checklist.{ci,review,mergeable}`, each `{status: "ok" | "pending" | "failed" | "unknown", detail}` (`status` is lowercase): the merge readiness shown by the UI and checked by the reducer;
  - `merge_error` (string): set when a merge ended in `not_mergeable`.
- Work item keys and repo keys are stored lowercase.
- `submit_action` events: source `ui`, payload `{actor, action, data}`, type `ApprovalGranted` (approve), `CancelRequested` (cancel) or `RetryRequested` (retry) or `MergeRequested` (merge). The last three are engine-internal and not part of the connector `EventType` set. A rejected `merge` (the actor lacks write access, or the readiness checklist is not all `ok`) is a reducer rejection, recorded in `transitions.note`, not a SQL error from `submit_action`.
- Columns beyond the docs: `transitions.event_type`, `jobs.deadline`, `jobs.created_at`. `work_items.project_id` is text (the Project name), exposed as `project` in the view.
- NOTIFY channels:
  - `workflow_events` (payload: event id), sent by ingest;
  - `work_item_changed` (payload: work item id), sent by the reducer.
- Runtime roles: `enzarb_connectors` gets `EXECUTE ingest_event`; `enzarb_ui` gets `SELECT` on the views and `EXECUTE submit_action`.

## 7. Browser → proxy

- **URL:** `wss://<host>/sandbox/v1/projects/<project>/mux?token=<jwt>`. Browsers can't set headers on websockets.
- **JWT:** HS256, signed with `ENZARB_SESSION_JWT_SECRET`, which ui and proxy share. Claims: `sub` (GitHub login), `project`, `aud: "enzarb-sandbox-proxy"`, `exp` (≤ 5 min after issue; it is checked only at connect).
- **Chat:** uses the same URL, token and authorization. The proxy's CTRL allowlist additionally admits `open{kind:"acp"}` and `credential_clear` (still not `run_*`), relays `acp` DATA byte for byte, and forwards `welcome.features` as described in section 4. `PROXY_IDLE_TIMEOUT_SECS` must be at least `ENZARB_CHAT_IDLE_SECS` (default 2100 s, 35 min).
- **Proxy Secret RBAC (ADR-0004 amendment, ADR-0013 amendment 2026-10-13):** a Role in `enzarb-sandboxes` only, on `secrets`: `get` (existing, namespace-wide), `create`, `update`, `patch`, `delete`. None can be pinned with `resourceNames`: the names are per owner and created at runtime, and `create` can never be restricted by name. The compensating controls are that the name is derived from the authenticated `spec.owner` and the `enzarb.dev/claude-credential` label is checked before update or delete.
- **Proxy authorization:** the proxy checks that `sub` is the Project's `spec.owner`, resolves `status.sandbox.endpoint` and the auth Secret, and dials sandbox-init with `client: "proxy"`.

### 7a. Browser realtime stream (enzarb-realtime)

- **URL:** `wss://<host>/live/v1/stream`, no query string.
- **Auth sources**, in precedence order; the first source present wins:
  1. `Authorization: Bearer <jwt>`, for non-browser clients. A present `Authorization` header is authoritative: if it is not `Bearer <non-empty>` (scheme case-insensitive), the result is HTTP 401 with no fall-through to the cookie or the query string.
  2. Cookie `enzarb_live`, for browsers: `Set-Cookie: enzarb_live=<jwt>; HttpOnly; Secure; SameSite=Strict; Path=/live/; Max-Age=300`, with no `Domain`. `Max-Age` equals the token's 5 min `exp` TTL (both from one clock read), so the cookie never outlives the token. The ui sets it from the signed-in session and clears it on sign-out and at login.
  3. `?token=<jwt>`, **deprecated** (see Deprecation).
- **Origin check:** applies to cookie auth only. The `Origin` header must exactly match an entry of `ENZARB_REALTIME_ALLOWED_ORIGINS`, a comma-separated list of `scheme://host[:port]` (http or https, no path; an invalid entry fails startup). When the variable is unset or empty, `Origin` must equal the `Host` header. A missing, `null`, unparsable or mismatching `Origin`: HTTP 403 before the upgrade. Bearer and query auth are not Origin-checked.
- **JWT:** HS256, signed with `ENZARB_REALTIME_JWT_SECRET`, which ui and enzarb-realtime share. Claims: `sub` (GitHub login), `projects` (array of Project names the user can see), `aud: "enzarb-realtime"`, `exp` (≤ 5 min after issue; checked at connect). The ui mints it from a remote function. An invalid or missing token from the selected source: HTTP 401 before the upgrade (Authorization and Origin cases: see Auth sources and Origin check).
- **Expiry:** the server closes the socket at `exp` (never later than 5 min after connect) with close code **4001**; the client fetches a fresh token, reconnects and refetches. The ui refreshes the `enzarb_live` cookie when it fetches the new token.
- **Deprecation:** a `?token=` connection logs a warn "token in query string is deprecated" with an in-process `deprecated_total` field (a log field, not a metric). `?token=` and the ui flag `ENZARB_REALTIME_LEGACY_TOKEN_URL` are removed once that log shows zero uses for 7 days.
- **Frames** (server to client, JSON text; client messages are ignored):
  - `{"topic":"work_item","id":123,"project":"enzarb"}`, sent only to clients whose `projects` contain `project`;
  - `{"topic":"resync"}`, sent to all clients: refetch everything. Sent after the service's LISTEN connection was re-established, when a work item's project could not be resolved, and when a client's bounded buffer overflowed.
- **Keepalive:** ping every 15 s; clients that do not pong are dropped. `GET /healthz` (liveness) and `GET /readyz` (200 only while LISTEN is connected).
- **Database:** the service `LISTEN`s on `work_item_changed` (section 6) and resolves id to project with `SELECT project FROM workflows_api.work_item_v WHERE id = $1`. Runtime role `enzarb_realtime` needs `USAGE` on `workflows_api` and `SELECT` on `workflows_api.work_item_v` only (follow-up: grant in `enzarb-workflows` migrations, pgop Role in `enzarb-helm`).
- **Routing:** `/live/` to enzarb-realtime:8080 (follow-up in `enzarb-helm`).

## 10. GitHub App

- **Permissions:** Issues RW, Pull requests RW, Contents RW, Workflows RW, Checks RW, Commit statuses R, Packages R, Metadata R. Read-write run tokens minted by `mint_clone_credential` (single repo) carry `contents`, `pull_requests` and `workflows` write so agents can edit `.github/workflows`; read tokens omit `workflows` (GitHub has no read level).
- **Deps token (`deps_token`):** the read-only multi-repo token from `mint_read_credential` (same-Project repos) carries `contents: read` and `packages: read`. The sandbox exposes it to the agent process only, as `ENZARB_DEPS_TOKEN` (cargo git deps) and `NODE_AUTH_TOKEN` (`npm ci` against npm.pkg.github.com), never written to disk. The App must be granted **Packages: Read** and each installation must accept it; until then GitHub rejects the request and the connector falls back to `contents: read` with a warning, so `npm ci` of private `@enzarb/*` packages returns 401.
- **Events:** issues, issue_comment, pull_request, pull_request_review, pull_request_review_comment, check_suite, check_run, status, installation, installation_repositories. Existing Apps must be updated for the new permission and events (see [oldie.md](oldie.md)).
- **Webhook URL:** `https://<host>/hooks/github`.
- **Install link and refresh:** `https://github.com/apps/<slug>/installations/new`. At sign-in the UI uses the user-to-server token once (never stored) to snapshot the repositories reachable through installations of this App (`GET /user/installations`, `GET /user/installations/{id}/repositories`) into `app.user_repositories`. `GET /login/github?refresh=1&return=<same-origin path>` re-runs that flow. Set the App's **Setup URL** to `<public>/login/github?refresh=1` with "Redirect on update" enabled so users land back in enzarb after installing.
- **Registration manifest:** `docs/github-app.yml` (setup in `docs/dev.md`). The same App also provides UI login (user authorization): its callback is `<public>/login/github/callback` (`callback_urls` in the manifest) and its Client ID/secret are the UI's `GITHUB_OAUTH_CLIENT_ID`/`GITHUB_OAUTH_CLIENT_SECRET`.

## 11. CI access to private enzarb dependencies

Library repos have read-only deploy keys. The org is on GitHub Free, so org secrets aren't visible to private repos; the private halves are **repo-level** secrets on each consuming repo: `ENZARB_PROTO_DEPLOY_KEY`, `ENZARB_CRDS_DEPLOY_KEY`, `ENZARB_CONNECTORS_DEPLOY_KEY`. Each key's comment is its repo's ssh URL, so `webfactory/ssh-agent` maps keys to repos. A repo with enzarb git dependencies adds this before building:

```yaml
env:
  CARGO_NET_GIT_FETCH_WITH_CLI: "true"
steps:
  - uses: actions/checkout@v4
  - uses: webfactory/ssh-agent@v0.9.1
    with:
      ssh-private-key: |
        ${{ secrets.ENZARB_PROTO_DEPLOY_KEY }}
        ${{ secrets.ENZARB_CRDS_DEPLOY_KEY }}
        ${{ secrets.ENZARB_CONNECTORS_DEPLOY_KEY }}
```
- Include only the keys the repo needs.
- npm `github:enzarb/enzarb-proto#main` dependencies fetch over ssh with the same agent. Set `git config --global url."ssh://git@github.com/".insteadOf "https://github.com/"` before `npm ci`.

## 12. Agent jobs (enzarb-workflows `engine::machine`)

- **Agent output:** the final message ends with exactly one fenced `json` block `{ "decision": "...", "body": "<markdown>" }`, with nothing after it. The machine reads it from `RunFinished.summary`.
- **Decisions per job kind:**
  - triage: `questions | ready | duplicate`
  - plan: `plan`
  - implement: `done | blocked` (for `done`, `body` is the PR description)
  - review: `approve | request_changes | comment`
  - address_comments: `done | blocked`
  - task: `reply | blocked`
  - A missing or invalid block → `Failed` (retryable).
- **Engine events:**
  - `JobSucceeded {job_id, kind, output}` / `JobFailed {job_id, kind, error}`, where `output` is the `RunFinished` fields (`summary, branch, head_sha, pushed`). Implement requires `pushed: true`.
  - `TimerFired {job_id?}`: with a `job_id` it is a job deadline, otherwise the work item's `wake_at`.
- **Handoff:** `StartWorkflow {key, workflow, event}`. The reducer inserts `event` (a synthesized `ChangeRequestOpened`) with dedupe key `handoff:<event.id>` in the same transaction.
- **Branches:**
  - read-only steps: `enzarb/<step>-<n>`
  - implement: `enzarb/issue-<n>`
  - review and address_comments: the PR's `head_ref`, used as both `base_ref` and `branch`.
- **Prompt templates:** `enzarb-workflows/crates/engine/prompts/*.md`. Untrusted text is wrapped in `<untrusted>` tags.

### Docker builds with private dependencies
- **Why not `--ssh default`:** it breaks once a repo needs more than one deploy key, because ssh offers the wrong key first.
- **Pattern** (see `enzarb-sandbox-proxy/Dockerfile`): pass each key as a build secret, e.g. `--secret id=proto_key`, `--secret id=crds_key`, `--secret id=connectors_key`. In the same `RUN`:
  1. write each key to `/root/.ssh/<name>_key`;
  2. add an ssh `Host gh-<name>` alias with `IdentityFile` and `IdentitiesOnly yes`;
  3. `git config url."ssh://git@gh-<name>/enzarb/<repo>".insteadOf "ssh://git@github.com/enzarb/<repo>"`;
  4. `cargo build --locked`;
  5. delete the keys.
- **CI:** run `docker build --secret id=<name>_key,env=<VAR>` with the repo-level deploy-key secrets in env. `docker/build-push-action`'s `secrets:` input mangles multi-line keys ("error in libcrypto").
- **Locally:** pass any key that has access (e.g. `--secret id=proto_key,src=$HOME/.ssh/id_ed25519`).

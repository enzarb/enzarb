# Cross-component contracts

Interfaces that more than one component depends on. Implementations must match this document. If a change needs a different shape, update this file in the same change (same PR in the `enzarb` monorepo, github.com/enzarb/enzarb) and say so in the PR.

## 1. Library dependencies

All components live in the monorepo (ADR-0015); library dependencies are path dependencies:

```toml
enzarb-proto            = { path = "../proto/crates/enzarb-proto" }
enzarb-crds             = { path = "../operator/crates/enzarb-crds" }
enzarb-connector        = { path = "../connectors/crates/connector" }
enzarb-connector-github = { path = "../connectors/crates/connector-github" }
```
- A library change and its consumers land in the same PR. Deployed components still roll out independently, so wire and schema changes stay backward compatible.
- `workflows_api` / `app_api` view and schema additions (new columns, view fields) must be backward compatible for one release: add, never rename or drop in the same release. Consumers should tolerate a missing new column for one chart version where practical. The main guard is the chart's migration ordering (workflows migrate before ui); the second is that a commit releasing several components publishes a single chart version pinning all of them (docs/ci.md "Releases").
- Crate paths:
  - `proto/crates/enzarb-proto`
  - `operator/crates/enzarb-crds`
  - `connectors/crates/connector`
  - `connectors/crates/connector-github`
- TS: `ui/` depends on `@enzarb/proto` via `"@enzarb/proto": "file:../proto"`; no registry is involved.

Shared choices across the Rust components:
- tokio, axum 0.8, tracing + tracing-subscriber (JSON logs), serde, thiserror/anyhow;
- sqlx (postgres, runtime-tokio, tls-rustls), kube + k8s-openapi (latest k8s feature), reqwest (rustls), jsonwebtoken;
- toolchain: stable, pinned in `rust-toolchain.toml` in each component dir, edition 2024.

## 2. `Project` CRD (`enzarb.dev/v1alpha1`, **cluster-scoped**)

Types are in the `enzarb-crds` crate; the CRD YAML is generated by `cargo run -p enzarb-crds --bin crdgen`.

```yaml
apiVersion: enzarb.dev/v1alpha1
kind: Project
metadata: { name: enzarb }            # DNS label, max 50 chars ("sb-<name>-workspace" ≤ 63)
spec:
  owner: ruckc                         # owner id (GitHub login of the creator)
  displayName: enzarb
  repositories:
    - url: https://github.com/enzarb/enzarb-ui    # canonical https URL
      connector: github
      defaultBranch: main
  runMode: worktree                    # worktree | fresh (fresh is post-MVP)
  triggers: { issues: true, changeRequests: true, mentions: true }
  sandbox:
    image: ""                          # empty = operator default (--sandbox-image)
    storage: 20Gi
    resources: {}                      # core/v1 ResourceRequirements
status:
  observedGeneration: 3
  namespace: enzarb-sandboxes          # the shared sandbox namespace (ADR-0013)
  sandbox:
    name: sb-enzarb                    # Sandbox CR name in that namespace: "sb-<project>"
    endpoint: ws://sb-enzarb.enzarb-sandboxes.svc:7070/v1/mux
    authSecretRef: { name: sb-enzarb-auth, key: token }   # in status.namespace
  conditions:                          # metav1.Condition, ordered for the UI checklist
    - type: ResourcesReady             # auth Secret, workspace + docker PVCs, NetworkPolicy
    - type: SandboxReady
    - type: Ready
```

Conditions: a failed step is `status: False` with a `reason` ending in `Failed`, `Failure` or `Error` (e.g. `NotOwnedError`: an object with the Project's name exists but has no owner), or the named terminal reason `InvalidSpec` (reported on `ResourcesReady`, for an invalid Project name and for a repository that another Project already owns, see "One Project per repository" below). Any other `False` reason is shown as in progress (e.g. `Terminating`: a deleted Project's objects with the same name are still being removed).

Objects per Project (ADR-0013), all in the shared namespace and labelled `enzarb.dev/project=<name>`: Sandbox `sb-<name>` (its pod and headless Service share the name; the Service is owned by the Sandbox), Secret `sb-<name>-auth`, PVCs `sb-<name>-workspace` and `sb-<name>-docker`, NetworkPolicy `sb-<name>`, each with a controller ownerReference to the Project. Names are at most 50 characters, enforced by a CEL rule in the CRD, the operator and the UI. Sandbox pods run as ServiceAccount `enzarb-sandbox` with no token and no RBAC: **no Kubernetes API access**; any future access is limited to other namespaces. Consumers find the sandbox only through `status.namespace` and `status.sandbox` (no derived fallback).

Defaults: `runMode: worktree`, all `triggers` true, `sandbox.storage: 20Gi`. Helpers in `enzarb-crds`: per-Project object names (`sandbox_name()`, `auth_secret_name()`, `workspace_pvc_name()`, `docker_pvc_name()`), `matches_repo()`, `RepoKey::from_url` / `RepoKey::from_connector_url` (github.com only for now; lowercases).

Resources and pod-shape changes: `spec.sandbox.cpu` (integer 1-64) and `spec.sandbox.memory` (`<int>Mi|Gi`, 512Mi-256Gi) set the sandbox container limits; the operator derives requests at 25% (floors 100m / 256Mi), and explicit `spec.sandbox.resources` win per key. Unset injects nothing. Any change to the desired pod shape (image, `ENZARB_*` env incl. `spec.maxRuns`, sandbox and dockerd resources, runtime class, mounts) is **queued, not applied**: the operator publishes `status.pendingChange {generation, since, reason}` and the informational condition `SandboxChangePending` (replaces `SandboxImageRoll`; no effect on `Ready`) and leaves the pod alone. After workflows has drained the sandbox it sets the Project annotation `enzarb.dev/drained-generation` to the `generation` it read (needs `patch` on `projects`); only an exact match releases the operator to delete the pod (never the Sandbox or PVCs). A newer spec change bumps `generation`, so an older ack no longer applies. Without an ack the operator applies the change after `--sandbox-roll-drain-timeout` (default 2h) from `since`. `pendingChange` is removed once the recreated pod matches. Storage growth is not queued (the PVC expands in place).

Repo key: a repository's **repo key** is `<connector>:<owner>/<repo>`, e.g. `github:enzarb/enzarb-ui`, always lowercase. Workflows and connectors route events by matching an event's repo key against the Projects' `spec.repositories`.

One Project per repository: a repo key (`RepoKey::from_connector_url`, compared case-insensitively) belongs to at most one Project. When several Projects list it, the oldest by `(metadata.creationTimestamp, name)` wins; `name` breaks timestamp ties and is unique because the CRD is cluster-scoped. Every other Project has `ResourcesReady=False` with the terminal reason `InvalidSpec`, like an invalid name; its message names the repository only, never the winning Project. Losing Projects must receive no events: workflows and connectors must route a repository's events only to the winner. That is the contract those components have to meet, not behaviour that exists today. The operator side is tracked in enzarb-sandbox-operator#19 (pending); the routing work is tracked in the follow-up issues linked from there.

Renaming: the owner may change `spec.displayName` (UI `setDisplayName`; owner-only, trimmed, non-empty, at most 100 characters). `metadata.name` is immutable. No sandbox restart: the display name is not part of the pod.

Changing repositories: the owner may replace `spec.repositories` after creation (UI `setRepositories`; same key-only, fresh-snapshot and one-Project-per-repository rules as creation; a repository already in the Project may be kept or removed without being in the snapshot, so archived repositories can be dropped). It takes effect without a sandbox restart and without drain-first (`status.pendingChange` is not used): repositories are not part of the sandbox pod. The workflows Project index is a watch and routes the next event by the new list; each run reads the list when it starts (deps token); the sandbox clones a repository when a job first needs it. Clones of removed repositories stay on the workspace volume until the Project is deleted; no new runs are routed to them.

## 3. sandbox-init

**Mux endpoint:** `ws://<pod>:7070/v1/mux`. Clients must send `Authorization: Bearer <token>`. The token is the `token` key of the Secret named in `status.sandbox.authSecretRef` (`sb-<project>-auth`) in `status.namespace`; the operator generates it, and it is mounted in the sandbox at `/var/run/enzarb/auth/token`.
- Allowed clients: `sandbox-proxy` and the workflows executor.
- Health: `GET :7070/healthz`. Body is JSON `{"status":"ok","dockerd":{"state":"starting|running|failed|stopped|disabled", ...}}`, always HTTP 200 (readiness never depends on Docker). `dockerd` is absent when the supervisor is not wired.

**Docker (ADR-0012, sidecar superseded by ADR-0016):** always on. The operator sets the pod `runtimeClassName` (`gvisor`) cluster-wide via `--sandbox-runtime-class`. Sandbox pod layout:
- One container, `sandbox`. No `dockerd` sidecar and no `docker-sock` volume.
- sandbox-init (pid 1) runs and supervises `dockerd` as root and drops everything else it spawns to uid/gid 1000 with no-new-privs. The `sandbox` container's `securityContext` overrides the pod-level non-root settings: `runAsUser: 0`, `runAsNonRoot: false`, `privileged: false`, `allowPrivilegeEscalation: true`, `drop: [ALL]` plus the gVisor Docker capability set (includes `SYS_ADMIN`, `NET_ADMIN`, `NET_RAW`, `SETUID`, `SETGID`, `CHOWN`). The pod-level `runAsUser`/`runAsGroup`/`fsGroup` (1000) stay. The kata profile is `privileged: true`.
- Volumes: `workspace` (PVC) at `/workspace`, `auth` (Secret) at `/var/run/enzarb/auth`, `docker-data` (PVC `sb-<name>-docker`) at `/var/lib/docker`.
- Env: `DOCKER_HOST=unix:///var/run/docker.sock` (group 1000, mode 0660), `ENZARB_DOCKERD_ARGS` (the runtime profile's dockerd flags). Optional sandbox-init env: `ENZARB_DOCKERD` (`off` disables), `ENZARB_DOCKERD_BIN`, `ENZARB_DOCKERD_SOCKET`, `ENZARB_DOCKERD_DATA_ROOT`, `ENZARB_DOCKERD_EXEC_ROOT`; pruning: `ENZARB_DOCKER_PRUNE` (`off` disables), `ENZARB_DOCKER_PRUNE_AGE` (default `24h`), `ENZARB_DOCKER_PRUNE_MIN_FREE` (default 15%), `ENZARB_DOCKER_BIN`.
- The image ships `dockerd`, `containerd`, `runc` and the `docker` CLI plus the buildx and compose plugins. Inner containers and builds default to `--network=host` through the image's `docker` wrapper (dockerd runs with `--iptables=false`); use `--user 1000:1000` so bind-mounted files stay editable.

**PTY channels:** CLOSE reason is `exit:<code>` or `signal:<n>`. A client half-close leaves the process running.

**Config (env):**
- Core: `ENZARB_LISTEN` (default `0.0.0.0:7070`), `ENZARB_AUTH_TOKEN_FILE`, `ENZARB_WORKSPACE` (`/workspace`), `ENZARB_SHELL`, `ENZARB_GRACE_SECS` (25; the pod's `terminationGracePeriodSeconds` must be larger).
- Runs: `ENZARB_MAX_RUNS` (2), `ENZARB_RUN_TIMEOUT_SECS` (3600), `ENZARB_CALLBACK_BACKOFF_MS`, `ENZARB_NET_RETRY_DELAYS_MS` (`10000,30000`: pauses before retrying a clone/fetch/push that failed on a transient network error; auth failures and rejected pushes are never retried), `ENZARB_PUSH_ATTEMPT_SECS` (120: wall-clock cap of one push attempt), `ENZARB_FETCH_ATTEMPT_SECS` (180: wall-clock cap of one clone/fetch attempt, so a dead host fails early; a timeout counts as transient and is retried; raise it for very large repos), `ENZARB_GIT_NAME`, `ENZARB_GIT_EMAIL`, `ENZARB_CLAUDE_TOKEN_FILE` (legacy only: the per-Project legacy file, read when `claude_token` is absent; removed with the fallback).
- Agent: `ENZARB_ACP_AGENT_BIN` (default `claude-agent-acp`), `ENZARB_CANCEL_GRACE_SECS` (10), `ENZARB_PERMISSION_POLICY` (YAML/JSON file; built-in default when unset).
- Chat (ADR-0014; sandbox-init config only, no Project spec field): `ENZARB_MAX_CHATS` (1; `0` disables chat and removes `acp` from `welcome.features`; chats never use `ENZARB_MAX_RUNS` slots), `ENZARB_CHAT_IDLE_SECS` (1800), `ENZARB_CHAT_MAX_SECS` (28800), `ENZARB_CHAT_RETENTION_DAYS` (7).
- Chat permission mode (ADR-0014 amendment 2026-10-12 (2); sandbox-init config only): `ENZARB_CHAT_PERMISSION_MODE` (`bypassPermissions` default | `default` | `plan`; other values fail startup; defaults to `default` when bypass is not allowed) and `ENZARB_CHAT_ALLOW_BYPASS` (true; `false` makes bypass unavailable, and `false` with an explicit bypass mode fails startup). Browser-bound `_enzarb/mode {sessionId, modeId, bypassAllowed}` is sent after session establishment and after each successful `session/set_mode`. The `session/set_mode` allowlist is {`bypassPermissions` (only while allowed), `default`, `plan`}. In bypass the agent sends no `session/request_permission` for ordinary tool calls, so `Policy::hard_deny` applies only in `default`/`plan`. Agent jobs are unchanged.

**Agent runs (ACP, ADR-0011):**
- sandbox-init is an ACP client of `@agentclientprotocol/claude-agent-acp` (pinned 0.88.0), one agent process per run, with cwd set to the worktree and `CLAUDE_CODE_OAUTH_TOKEN` in its environment.
- **Protocol steps:** `initialize`, then `session/new` (mode `default`), then `session/prompt`.
- **Permissions:** every `session/request_permission` is answered by the policy with `allow_once` or `reject_once`, never persistent options.
  - Edits are limited to the worktree.
  - Reads (Read/Grep/Glob and read-only shell utilities) may also reach the Project's other repo checkouts and worktrees (`/workspace/repos`, `/workspace/worktrees`). Writes, `cd` and docker bind mounts stay inside the run's own worktree (enzarb-sandbox-container#27).
  - `git -C <dir>` is allowed only for a `<dir>` in the read roots and a read-only subcommand (`status`, `log`, `show`, `diff`, `rev-parse`, `ls-files`, `ls-tree`, `grep`, `blame`, `branch --list`, `cat-file`).
  - Secrets are unreadable under any root: `.enzarb` (including the legacy `claude-token`), `.git-credentials`, `.gitconfig`, `.netrc`, git credential helper config.
  - Commands must match the allowlist; shell metacharacters and expansions are denied.
  - Network fetch is denied unless the host is allowlisted.
- **Summary:** the verbatim agent text of the turn. `exit_code` is 0 on `end_turn`, the agent's code on a crash, and null when cancelled or timed out.
- **Cancel:** `session/cancel`, then a grace period, then the process group is killed.

**Interactive chat (ACP, ADR-0014; [design](design/chat-tab.md)):**
- One `acp` mux channel is one `claude-agent-acp` child, in its own process group. DATA_BIN carries newline-delimited JSON-RPC (max line 4 MiB). sandbox-init is a filtering relay: it forces `clientCapabilities` to none, `cwd` to the chat worktree and `mcpServers` to `[]`, allows only `initialize`, `session/new`, `session/load` (registered sessions only), `session/prompt`, `session/cancel` and `session/set_mode` (`default` or `plan`), and redacts the Claude token.
- **Permissions:** `Policy::hard_deny` rejects (`reject_once`) secrets, `.enzarb`, the mux auth token, edits outside the chat worktree, `git push` and non-allowlisted fetches, and notifies the browser with `_enzarb/permission_denied`. Every other request goes to the user; only `allow_once`, `reject_once` or `cancelled` answers are accepted, and anything else becomes `reject_once`. No path auto-approves.
- **Environment:** the Claude token only. A chat never receives `clone_token`, `deps_token` or `npm_token`, so it cannot push or install private packages.
- **Limits:** at `ENZARB_MAX_CHATS` a new open closes the existing chat with `superseded`; 1 `acp` channel per socket; prompts up to 256 KiB. Chat does not block drain.
- **CLOSE reasons on an `acp` channel:** `idle`, `superseded`, `shutdown` (sandbox-init got SIGTERM), `limit` (hard lifetime or line cap), `exit:<n>`, `signal:<n>`.

**Image build:** `docker buildx build -f sandbox-container/Dockerfile --load .` from the repo root (path dependency on `proto/`). The minimal runtime image (ADR-0012, enzarb-sandbox-container#16) contains:
- sandbox-init;
- node 24 + claude-agent-acp + the glibc `claude` binary;
- mise;
- build-essential, pkg-config, libssl-dev;
- git, ca-certificates, openssh-client.

Plus curl (mise's Rust backend needs it for rustup) and Docker 29.8.2 (static bundle: `dockerd`, `containerd`, `runc`, the `docker` CLI, with the buildx and compose plugins; ADR-0016). No Rust, npm or extra CLI tools.

**Toolchains (mise, per project, persisted on the PVC):**
- `MISE_DATA_DIR=/workspace/.toolchains/mise`, `MISE_CACHE_DIR=/workspace/.toolchains/cache`, `CARGO_HOME=/workspace/.toolchains/cargo`, `RUSTUP_HOME=/workspace/.toolchains/rustup`.
- `MISE_TRUSTED_CONFIG_PATHS=/workspace`, `MISE_YES=1`, `MISE_IDIOMATIC_VERSION_FILE_ENABLE_TOOLS=rust`.
- `PATH` includes the mise shims, so a repo's `mise.toml` or `rust-toolchain.toml` determines its tools.

**Transcript records** (`transcript.jsonl`, also streamed on `log_channel`). Each has `ts` and `kind`:
- `state {state, branch?}`
- `worktree {path, branch, start, base}`
- `log {source: git|acp, line}`
- `acp {event: initialized|session|cancel, …}`
- `update {session_id, update}` (the raw ACP `session/update`)
- `permission {tool_call_id, tool_kind, title, input, decision, rule, reason, option_id}`
- `agent_result {stop_reason, text}`
- `finished {outcome, exit_code, head_sha, pushed}`

Secrets are redacted from all records.

**Filesystem (on the PVC):**
- `/workspace`: repos and worktrees.
- `/workspace/.toolchains/`: mise data and cache, cargo, rustup.
- `/workspace/repos/<slug>-<hash>/`: one clone per repo URL.
- `/workspace/worktrees/run-<run_id>/`: the run's worktree. It starts from `origin/<branch>` if that exists, otherwise from `base_ref`. It is deleted when the run ends (the branch stays in the clone); at sandbox-init startup and before each run, `run-*` dirs of no active run are pruned.
- `/workspace/.enzarb/runs/<run_id>/`: `state.json`, `request.json` (0600, clone token blanked), `transcript.jsonl`, and `callback.json` while a callback is pending.
- `/workspace/worktrees/chat-<chat_id>/`: a chat's worktree (`chat_id` is 16 random hex chars), detached at `origin/<default branch>` of the chosen clone; commits go on the local branch `enzarb/chat-<chat_id>`. `run-*` pruning never touches it; a sweep removes chat worktrees with no live channel and no activity for `ENZARB_CHAT_RETENTION_DAYS`.
- `/workspace/.enzarb/chats/<chat_id>/`: `meta.json` (`acp_session_id`, `repo`, `worktree`, `created`, `last_active`) and `transcript.jsonl` (0600; same record kinds as runs, plus `prompt`).
- `/workspace/.enzarb/chat-home/.claude`: `CLAUDE_CONFIG_DIR` for chat agents, so `session/load` survives pod restarts.
- `/workspace/.enzarb/claude-token`: mode 0600. Legacy per-Project token, read only while `claude_token` is absent from `run_start`/`open`. On connect sandbox-init promotes it with `credential_captured{legacy:true}` (first Project wins), then deletes it when the proxy answers `credential_state{configured:true}`. New captures are never written to disk.

## 4. proto messages

The wire format (frame layout, flow control) is defined in `proto/docs/protocol.md`. Frame types: `CTRL, DATA_BIN, DATA_JSON, WINDOW, CLOSE`.

CTRL payloads are JSON objects tagged by `"type"` and use channel 0:

| Message | Direction | Fields |
|---|---|---|
| `hello` | client → server | `versions: [1]`, `client: "ui" \| "proxy" \| "executor"` |
| `welcome` | server → client | `version`, `features?: [string]` (optional; `"acp"` when chat is enabled; absent means none) |
| `open` | client → server | `channel`, `kind: "pty" \| "acp"`, `cols`, `rows`, `command?: [..]`, `repo?`, `resume?`, `claude_token?` (acp only; set by the proxy) (see below) |
| `opened` / `open_error` | server → client | `channel` / `channel, message, code?` |
| `resize` | client → server | `channel`, `cols`, `rows` |
| `run_start` | client → server | see below |
| `run_accepted` | server → client | `run_id`, `state`, `existing: bool` |
| `run_status` → `run_state` | both | `run_id` → `run_id, state, exit_code?, summary?, usage?` |
| `run_cancel` | client → server | `run_id` |
| `credential_captured` | server → client | `kind: "claude_oauth"`, `token?` (the captured token; **proxy-only**: the proxy consumes the frame, encrypts and stores the token in Postgres, never forwards it to the browser and never logs it), `legacy?: bool` (a promoted legacy file: store only if the user has no token) |
| `credential_status` | client → server | (none); browsers may send it |
| `credential_state` | server → client | `kind: "claude_oauth"`, `configured: bool`, `scope?: "user"` (the Claude token is per user, ADR-0004 amendment 2026-10-13). The proxy also sends it to the sandbox as the answer to a `legacy` capture |
| `credential_clear` | client → server | `kind: "claude_oauth"`; browsers may send it (on the proxy's allowlist). The proxy handles it locally by deleting the owner's row (`claude_credential_delete`) and answers `credential_state{configured:false, scope:"user"}`; it is not forwarded to the sandbox |
| `error` | both | `code`, `message`, `run_id?`, `channel?` (a `run_id` routes the error to that run's pending request) |

**Claude token (per user, ADR-0004 amendment 2026-10-13):** one encrypted row per user in Postgres (`app.claude_credentials`, see [database.md](database.md)), keyed by the authenticated `spec.owner`, never by frame content. No Kubernetes Secret holds it, and the sandbox keeps no copy on disk. The proxy is the only writer of put, rekey and sandbox-initiated clear (it consumes `credential_captured`, and handles `credential_clear`); the UI may delete only its own row, through `app_api.claude_credential_delete_own(owner)` (the owner is the session login), so Remove needs no running sandbox. The ciphertext is readable only by the proxy and the workflows executor, and the UI sees presence and `updated_at` only (`app_api.claude_credential_v`). Delivery is additive in proto (protocol version stays 1; old decoders ignore the fields):
- **Jobs:** `run_start.claude_token` (optional), set by workflows per run from the Project owner's row, like `npm_token`. It is not stored in `jobs.input`, not written to `request.json`, state, callback files or the legacy file, exposed only as `CLAUDE_CODE_OAUTH_TOKEN` to the agent process, redacted (and its encodings) from transcripts, summaries and callbacks, and redacted in `RunStart` debug output. An owner without a row fails the job before dispatch with a non-retried "owner has no Claude credential" (`no_credential`).
- **Chats:** `open{kind:"acp"}` gains `claude_token` (optional), set **only by the proxy** when it forwards the browser's `open` to the sandbox. The proxy drops any browser-supplied value, and answers the browser with `open_error{code:"no_credential"}` itself when the owner has no row. sandbox-init puts it in the chat child's environment only.
- **Fallback during rollout:** the sandbox image rolls out first (ADR-0004 Rollout order), before the proxy and workflows enforce `no_credential`, so legacy files are promoted before enforcement. Until removal, when `claude_token` is absent sandbox-init still reads the legacy `/workspace/.enzarb/claude-token` if present; otherwise it answers `no_credential`. The fallback is removed once every sandbox runs the new image and the proxy has logged no `legacy` capture for 7 days.
- **Logging:** Debug and tracing output of the `open` frame and of `claude_credential_get` results (proxy and workflows) redacts `claude_token`, as `RunStart` debug output does. `credential_captured.token` is never logged either.

**`acp` channels (ADR-0014; additive, protocol version stays 1):**
- `kind: "acp"` opens a byte stream of newline-delimited JSON-RPC (ACP) in DATA_BIN; messages may span frames. `cols`/`rows` are ignored (clients send `0`). `repo` (optional) names a Project repo URL that must already be cloned; `resume` (optional) is the ACP session id, informational only.
- **`welcome.features`:** the sandbox sends `["acp"]` when `ENZARB_MAX_CHATS > 0`. The proxy answers the browser's `hello` itself and forwards the sandbox's features intersected with those it can guard. Decoders ignore unknown fields.
- **Compatibility rule:** a sender must not send `open{kind:"acp"}` before seeing `"acp"` in `welcome.features`. A proxy that cannot decode a frame closes the socket with 1008, so an `acp` open to an old proxy would kill the connection.
- **`open_error.code`** (optional): `chat_disabled`, `chat_limit`, `no_credential`, `repo_not_cloned`, `unsupported_kind`. Clients must tolerate other values. An unknown `kind` decodes (Rust `ChannelKind::Unknown`) and yields `unsupported_kind`.
- **CLOSE reasons** on an `acp` channel: `idle`, `superseded`, `shutdown`, `limit`, `exit:<n>`, `signal:<n>`. Clients must tolerate other text.

`run_start` fields:

```json
{ "type": "run_start", "run_id": "job-123",
  "repo_url": "https://github.com/enzarb/enzarb-ui", "base_ref": "main",
  "branch": "enzarb/issue-42", "push": true,
  "clone_token": "<short-lived installation token>",
  "prompt": "…", "timeout_secs": 3600,
  "callback_url": "http://enzarb-workflows-executor.enzarb.svc:8081/v1/runs/job-123/finished",
  "callback_token": "<hex HMAC-SHA256(executor secret, run_id)>",
  "log_channel": null,
  "deps_token": "<optional, omitted when absent>",
  "npm_token": "<optional, omitted when absent>",
  "claude_token": "<optional: the Project owner's Claude token, omitted when absent>" }
```
- **`claude_token`** (optional, additive): see "Claude token" above.
- **`npm_token`** (optional, additive): a **long-lived** token with `read:packages`, for `npm ci` of private `@enzarb/*` packages on npm.pkg.github.com. GitHub App installation tokens cannot read org packages even with `packages: read` (E403 "Permission installation not allowed to Read organization package"), so `deps_token` cannot serve that role. The workflows executor reads it from `ENZARB_NPM_TOKEN` / `ENZARB_NPM_TOKEN_FILE` (in the chart: Secret `enzarb-updater-registry`, key `registry-token`) and sets it on implement, address-comments, resolve-conflicts and review runs only; it is never stored in `jobs.input`. sandbox-init exposes it to the agent process only, as `NODE_AUTH_TOKEN` (it takes precedence over the `deps_token` fallback; `ENZARB_DEPS_TOKEN` keeps feeding cargo/git), redacts it (and its basic-auth base64 forms) from transcripts, summaries and callbacks, and never writes it to `request.json`, state, callback files or an `.npmrc`. Debug output of `RunStart` redacts it. Absent means `NODE_AUTH_TOKEN` falls back to `deps_token`.
- **`retarget`** (optional, additive; stacked change requests): `{head_ref, onto, old_base, expected_sha, protected?: [string]}` turns the run into a **retarget run**. After a parent change request was squash-merged, sandbox-init rebases enzarb's own child branch, `git rebase --onto origin/<onto> <old_base>` of `head_ref`, and pushes it. `onto` is the default branch, `old_base` the parent head sha the child was cut from, `expected_sha` the child head the push lease expects. No agent, toolchain or Claude token is involved, and `prompt`, `push`, `branch` and `base_ref` are ignored. This is the **only force-push in enzarb**; it lives in `sandbox-container/src/retarget.rs` alone (a test fails if another source file names the force flags). Containment, in order:
  1. Rejected without any git call (`rejected`) unless `head_ref` starts with `enzarb/` (the engine's branch prefix) and is not `onto`, not in `protected`, and has plain ref syntax (no leading `-`, `..`, `:`, whitespace, `~^?*[\`), `old_base` and `expected_sha` are 40-hex lowercase shas, and `onto` is a valid branch name.
  2. After a hardened fetch: the remote head must equal `expected_sha` (`lease_failed`), `old_base` must be an ancestor of it (`not_ancestor`), and every non-merge commit in `old_base..head` must have the sandbox's own configured git author, name and email both (`foreign_commits`). A human's commits are never rewritten.
  3. The rebase runs in a throwaway detached worktree; a conflict is aborted and nothing is pushed (`conflict`).
  4. The push uses the normal hardened path (token only in the environment, no hooks) with `--force-with-lease=refs/heads/<head_ref>:<expected_sha>` and the single refspec `<new_sha>:refs/heads/<head_ref>`. A refused lease is `lease_failed`.

  The run finishes `succeeded` with `summary` a single-line JSON object `{"outcome": "retargeted|conflict|lease_failed|not_ancestor|foreign_commits|rejected", "head_sha": "<pushed sha for retargeted, else the current remote head, may be empty>", "reason": "<text>"}`, and `pushed` true only for `retargeted`. Infrastructure failures (network, auth, cannot run git) still end `failed`.
- **Wire details** (`proto/docs/protocol.md` and the `enzarb_proto::Ctrl` enum are the source of truth):
  - 10-byte big-endian header: type, flags (0), channel u32, length u32. Max payload 1 MiB, one frame per websocket binary message.
  - 256 KiB initial window per channel and direction. `CLOSE` is a half-close.
  - Optional fields are omitted when absent; `null` is accepted on decode.
- **`run_state`** is sent in reply to `run_status` and also pushed whenever a run changes state.
- **`log_channel`:** a non-null value is a channel the client chooses. `run_accepted` implicitly opens it, and the server streams transcript lines on it as `DATA_JSON`.
- **`RunFinished`** (`enzarb_proto::RunFinished`) is the callback's HTTP body, not a CTRL message. `exit_code` is optional because cancelled runs may have none.
- **`usage`** (`enzarb_proto::Usage`, optional on `RunFinished` and `run_state`; additive, old decoders ignore it and old senders omit it): `{input_tokens?, output_tokens?, cache_read_input_tokens?, cache_creation_input_tokens?, models?: [string], cost_usd?}`. A field the agent did not report is **absent**, never 0. `cost_usd` is the cost as reported by Claude (`total_cost_usd`, or the `cost` of ACP `usage_update`), even on a subscription token; nothing computes or estimates it. The whole object is absent when the agent reported nothing. `input_tokens` is the **uncached** input only; the UI shows total input (`input_tokens` + `cache_read_input_tokens` + `cache_creation_input_tokens`) as "in".
- **Idempotent:** a repeated `run_id` returns the existing run.
- **States:** `queued | running | succeeded | failed | cancelled`.
- **What the run does:**
  1. ensures the repo clone and creates worktree `run-<run_id>` on `branch` from `base_ref`;
  2. runs the ACP agent with the prompt (see Agent runs above);
  3. if `push`, pushes `branch` with `clone_token`.

**Run finished callback:**
- **Request:** `POST callback_url` with `Authorization: Bearer <callback_token>`. sandbox-init retries with backoff until it gets a 2xx.
  ```json
  { "run_id": "job-123", "outcome": "succeeded|failed|cancelled", "exit_code": 0,
    "summary": "<claude result text>", "branch": "enzarb/issue-42",
    "head_sha": "abc…", "pushed": true }
  ```
- **Fallback:** the executor also polls `run_status` for jobs past their deadline.
- **Comments:** the executor posts comments to GitHub. Sandboxes never get a GitHub token other than the repo-scoped `clone_token`.

## 5. Normalized events (`enzarb-connector` crate → `workflows.events.payload`)

```json
{ "specversion": "1.0", "source": "github", "id": "<delivery id>", "type": "CommentAdded",
  "subject": "github:enzarb/enzarb-ui#42", "time": "2026-10-08T12:00:00Z",
  "data": {
    "repo": "github:enzarb/enzarb-ui",
    "actor": { "login": "ruckc", "id": 42, "is_bot": false },
    "item": { "kind": "issue|change_request", "number": 42, "url": "…", "title": "…", "body": "…",
              "author": "ruckc", "head_ref": null, "base_ref": null, "head_sha": null },
    "comment": { "id": 987, "body": "…", "url": "…" }
  } }
```
- **Rust types:** `enzarb_connector::{Event, EventData, EventType}` are the source of truth for field shapes. `review.state` is a free string.
- **`type`:** one of `WorkItemOpened, CommentAdded, Mentioned, ApprovalGranted, ChangeRequestOpened, ChangeRequestUpdated, ReviewSubmitted, WorkItemClosed, CiStatusChanged, WorkItemLabeled`.
  - `WorkItemClosed` carries `data.merged: bool`.
  - `WorkItemLabeled` carries `data.label` (the label name) and `actor` (who added it). Additive. A connector reports only the labels the engine acts on: GitHub sends the `epic` label of an issue (`issues.labeled`). Consumers that do not know the type ignore it.
  - `ReviewSubmitted` carries `data.review: {id, state, body}`.
  - `CiStatusChanged` carries the optional `data.ci`, **one per check run, check suite or commit status** (not an aggregate): `{head_sha, state: "success" | "failure" | "pending", context?, url?}` (`state` is lowercase). Additive: consumers that ignore `CiStatusChanged` or `data.ci` are unaffected. Aggregation into one CI verdict happens in `get_merge_readiness` (below); the rule is in `docs/connectors.md`.
- **`subject`:** the work item key, `<repo key>#<number>`. Issues and PRs share GitHub's number space, so `#` is used for both.
- **`ApprovalGranted`:** a `/approve` comment on its own line, or the label `enzarb:approved`.
- **`Mentioned`:** `@<bot handle>` in a comment or issue body (handle configurable, default `enzarb`).
- **Bot actor:** events whose actor is the bot itself are dropped by the receiver. The one exception is `WorkItemOpened` for an issue whose body carries an epic marker (`<!-- enzarb:epic=<parent key>:<sub-issue key> -->`, [adr/0018](adr/0018-epics.md)); the engine decides whether to accept it.
- **Derived events:** one delivery can produce several events. The primary event keeps the delivery id; derived ones get `<delivery>#mentioned` and `<delivery>#approved`, so the dedupe key is `github:<event id>`.
- **Mentions and approval on PRs:** `Mentioned` also fires from a PR body when the PR is opened, and the approval label works on PRs as well as issues.
- **API:** `enzarb_connector_github::normalize(...)` returns `Normalized::Events{events}` or `Normalized::Installation{change}`.
- **Merge methods** (additions to the `Connector` trait, see [connectors.md](connectors.md#outbound-the-connector-trait)). Squash is the only merge method.
  - `merge_change_request(item, number, expected_head_sha, commit_title, commit_body?, idempotency_key) -> MergeOutcome`. The merge is pinned to `expected_head_sha`. `MergeOutcome` is `merged{sha} | already_merged{sha?} | head_moved | not_mergeable{reason}`.
  - `set_base(item, number, new_base, idempotency_key)`: changes a change request's base branch (GitHub `PATCH /pulls/{n}` with `base`); setting the base it already has succeeds. Used only to retarget a stacked change request.
  - `delete_branch(repo, branch, idempotency_key)`: deletes a branch; one that is already gone succeeds. Default implementation: unsupported. Used only to delete the head branch after a merge the user asked for.
  - `get_merge_readiness(item, number) -> MergeReadiness{head_sha, mergeable: Option<bool>, mergeable_state, ci, ...}`. It aggregates CI (all checks and statuses on the head; no CI counts as passing). The remaining fields and the `mergeable_state` values are defined by `enzarb_connector::MergeReadiness`.

## 6. `workflows_api` (Postgres, owned by `workflows/`)

> **Naming:** the product calls a work item a **task** (UI copy, route `/task/<id>`). The database objects, `NOTIFY work_item_changed` and the Rust identifiers below keep the `work_item` names for now: renaming them is a separate, additive change (new `task` names with `work_item` aliases) so deployed components keep working.

```sql
workflows_api.ingest_event(p_source text, p_dedupe_key text, p_work_item_key text,
                           p_type text, p_payload jsonb) RETURNS bigint   -- NULL if duplicate
workflows_api.submit_action(p_work_item_id bigint, p_actor jsonb, p_action text,
                            p_payload jsonb) RETURNS bigint               -- actions: approve | cancel | retry | merge | comment
-- views
workflows_api.work_item_v(id, key, project, workflow, state, state_data, created_at, updated_at,
                          waiting_for, resumes_at, usage_totals, waiting_on, wait_reason, wait_text,
                          blocked_by_dependency)
workflows_api.work_item_dependency_v(work_item_key, depends_on_key, source, via, status, state, title, url)
workflows_api.transition_v(id, work_item_id, from_state, to_state, event_type, at)
workflows_api.job_v(id, work_item_id, kind, status, attempt, created_at, updated_at, output, waiting_for, resumes_at, usage)
```
- View columns are append-only; existing consumers select by name.
- **`job_v.usage`** (jsonb, nullable): token usage and cost summed over all runs of the job (session-limit waits, restart retries and the recovery run each add their run), in the `Usage` shape of section 4. Keys are absent when no run reported them; `NULL` when nothing was reported. A run is counted once (by `run_id`), for any outcome including failed and cancelled.
- **`work_item_v.usage_totals`** (jsonb, nullable): per key, the sum over the item's jobs that reported it, plus the union of `models`. A key no job reported is absent (so `cost_usd` is absent, not 0, when no job reported a cost); `NULL` when no job has usage. Cost is as reported by Claude, not an estimate.
- Changes to `jobs.usage` send `work_item_changed`.
- **Dependencies** ([ADR-0017](adr/0017-work-item-dependencies.md)): `work_item_dependency_v` lists each effective dependency of `work_item_key` (filter on `depends_on_key` for dependents). `source` is `github`, `text` or `comment`; `via` is the issue key when a change request inherited it; `status` is `done` (Done/Merged), `closed` (Cancelled/Closed/Duplicate: will not complete), `open` or `pending` (no work item yet). `work_item_v.blocked_by_dependency` is true while a change request's `state_data.open_dependencies` is not empty, and `state_data.checklist.dependencies` is a fourth check in the shape above. Changes to the table send `work_item_changed` for both ends. Event type `DependenciesChanged` (source `engine`, payload `{}`) is engine-internal.
- Both functions are `SECURITY DEFINER`.
- Connectors use dedupe key `github:<event id>`; the UI uses `ui:<uuid>`. Events the engine itself generates use source `engine` (`handoff:<id>`, `timer:…`, `job:<id>:<attempt>`).
- `transitions.work_item_id` is nullable: events that are ignored (no Project, no workflow) get a `to_state='ignored'` row with no work item. `transitions.note` records rejections.
- `work_items.state_data` carries `title` and `url` for display. For `change_request` items it may also carry (additive):
  - `checklist.{ci,review,mergeable}`, each `{status: "ok" | "pending" | "failed" | "unknown", detail}` (`status` is lowercase): the merge readiness shown by the UI and checked by the reducer;
  - `merge_error` (string): set when a merge ended in `not_mergeable`, or when a stacked retarget was parked (the reason);
  - stacked change requests (all optional strings/booleans, absent or empty when not stacked; see [workflows.md](workflows.md#change_request)): `stacked_on` (work item key of the parent change request), `stack_parent_ref` (the parent's branch, the current `base_ref`), `stack_parent_tip` (the parent head the child branch was cut from), `default_base` (the branch to retarget onto), `stack_parent_merged`, `stack_parent_closed`, `retargeting` (a `retarget_change_request` job is in flight) and `retarget_attempts`. The keys are cleared once the change request is retargeted or parked;
  - `auto_rounds`, `auto_trigger`, `auto_capped`: bookkeeping for automatic fix rounds (see `docs/workflows.md`).
  - `wait` (object or null in final states) `{waiting_on, reason, text, url?}`: why the item is waiting, derived by `workflows` on every transition. `waiting_on` is `human` | `enzarb` | `ci` | `github`; `work_item_v.waiting_on`, `wait_reason` and `wait_text` expose `waiting_on`, `reason` and `text` (NULL until the item's next transition after the migration; clients fall back to the state). `human` means Needs you. Reason codes: `awaiting_review` (human), `ready_to_merge` (human), `enzarb_failed` (human), `conflict_parked` (human), `reviewing`, `addressing_comments`, `resolving_conflict`, `ci_failed_fixing` (no longer emitted: a CI failure starts a fix round, which is `enzarb_fixing`; clients still accept the code in persisted data), `changes_requested_fixing`, `enzarb_fixing` (an automatic fix round on enzarb's own review findings is running) (all enzarb), `ci_pending` (ci), `merging` (github). `ci_failed` (human) is emitted in `AwaitingChanges` when CI failed on the reviewed head and no fix round is running (rounds used up, or `ENZARB_MAX_AUTO_ROUNDS=0`): `text` is "CI failed: <checks>", `url` the first failing check; the UI offers Retry, which starts a CI-fix round. `round_limit` (human) is emitted when the automatic fix round cap is reached. `checks_unverified` (human) replaces `awaiting_review` when enzarb's review is `comment` because checks did not pass: `text` lists each check with its reason (`refused`, `missing_tool`, `timeout`, `not_attempted`, `covered_by_ci`); a write-access GitHub approval, `/approve` or the UI approve sets the review check to OK. `ci_stale` (human) is emitted when CI has been pending or unknown for 30 minutes on an approved head. The ticker re-asks the connector about such items with backoff (60 s to 15 min) through the engine-internal event `ReadinessPoll` (payload `{}`). Clients treat unknown reasons as blocked. Reserved for later, not emitted yet: `decision_needed` (human, with `url` of the comment).
- Work item keys and repo keys are stored lowercase.
- `jobs.kind` is plain text; `create_sub_issues` (additive; not an agent job) has input `{item, depth, sub_issues: [{key, title, body, depends_on}]}` (in creation order) and output `{children: [{key, item, title}]}`. It calls `Connector::create_issue` and `link_sub_issue` and is idempotent: repeating it creates nothing twice. Issue `state_data` gains, all optional: `epic`, `epic_depth`, `epic_parent`, `sub_issues`, `children`, `open_dependencies`, `children_notified`; the issue states `Decomposing` and `AwaitingChildren` are new. `work_item_dependencies.source` gains `epic` (an epic waits for its sub-issues; a sub-issue waits for what the plan orders before it).
- `submit_action` data (both additive):
  - `comment` takes `data.body` (text, 1 to 20000 characters; `submit_action` rejects anything else). It is feedback on an issue, valid while the plan awaits approval or questions await answers. Workflows posts the text to the issue (`post_comment`, idempotency key from the event) and handles it like the same comment written on GitHub: plan feedback re-plans, an answer from the author resumes triage. Anyone else, an empty text or any other state is a reducer rejection (`transitions.note`).
  - `merge` takes an optional `data.delete_branch` (bool, default false). After a successful merge workflows deletes the head branch with `Connector::delete_branch`, best effort: a failure is recorded in `transitions.note` and never fails the merge. Only `enzarb/...` branches are deleted, and not while an open change request is still stacked on it (see [workflows.md](workflows.md)); the note says why.
- `submit_action` events: source `ui`, payload `{actor, action, data}`, type `ApprovalGranted` (approve), `CancelRequested` (cancel), `RetryRequested` (retry), `MergeRequested` (merge) or `CommentAdded` (comment; connector `CommentAdded` events have no top-level `action`). All but `ApprovalGranted` and `CommentAdded` are engine-internal and not part of the connector `EventType` set. A rejected `merge` (the actor lacks write access, or the readiness checklist is not all `ok`) is a reducer rejection, recorded in `transitions.note`, not a SQL error from `submit_action`.
- `jobs.kind` is plain text; `retarget_change_request` (additive; not an agent job) has input `{item, number, head_ref, expected_sha, old_base, onto}` and output `{outcome, head_sha?, reason?, base_set?}` with `outcome` one of `retargeted`, `already_retargeted`, `conflict`, `lease_failed`, `not_ancestor`, `foreign_commits`, `rejected`. It runs as a sandbox retarget run (`RunStart.retarget`) and is the only job that force-pushes.
- Columns beyond the docs: `transitions.event_type`, `jobs.deadline`, `jobs.created_at`. `work_items.project_id` is text (the Project name), exposed as `project` in the view.
- NOTIFY channels:
  - `workflow_events` (payload: event id), sent by ingest;
  - `work_item_changed` (payload: work item id), sent by the reducer.
- Runtime roles: `enzarb_connectors` gets `EXECUTE ingest_event`; `enzarb_ui` gets `SELECT` on the views and `EXECUTE submit_action`.

## 7. Browser → proxy

- **URL:** `wss://<host>/sandbox/v1/projects/<project>/mux?token=<jwt>`. Browsers can't set headers on websockets.
- **JWT:** HS256, signed with `ENZARB_SESSION_JWT_SECRET`, which ui and proxy share. Claims: `sub` (GitHub login), `project`, `aud: "enzarb-sandbox-proxy"`, `exp` (≤ 5 min after issue; it is checked only at connect).
- **Chat:** uses the same URL, token and authorization. The proxy's CTRL allowlist additionally admits `open{kind:"acp"}` and `credential_clear` (still not `run_*`), relays `acp` DATA byte for byte, and forwards `welcome.features` as described in section 4. `PROXY_IDLE_TIMEOUT_SECS` must be at least `ENZARB_CHAT_IDLE_SECS` (default 2100 s, 35 min).
- **Claude token (ADR-0004 amendment 2026-10-13):** the proxy needs a Postgres role (`enzarb_sandbox_proxy`) and the keyring Secret `enzarb-claude-key`, but **no new Secret RBAC** in `enzarb-sandboxes` (ADR-0013 unchanged). On the mux connection it strips browser-supplied `claude_token`, injects the owner's on `acp` opens, consumes `credential_captured` and handles `credential_clear` itself.
- **Proxy authorization:** the proxy checks that `sub` is the Project's `spec.owner`, resolves `status.sandbox.endpoint` and the auth Secret, and dials sandbox-init with `client: "proxy"`.

### 7a. Browser realtime stream (enzarb-realtime)

- **URL:** `wss://<host>/live/v1/stream`, no query string.
- **Auth sources**, in precedence order; the first source present wins:
  1. `Authorization: Bearer <jwt>`, for non-browser clients. A present `Authorization` header is authoritative: if it is not `Bearer <non-empty>` (scheme case-insensitive), the result is HTTP 401 with no fall-through to the cookie or the query string.
  2. Cookie `enzarb_live`, for browsers: `Set-Cookie: enzarb_live=<jwt>; HttpOnly; Secure; SameSite=Strict; Path=/live/; Max-Age=300`, with no `Domain`. `Max-Age` equals the token's 5 min `exp` TTL (both from one clock read), so the cookie never outlives the token. The ui sets it from the signed-in session and clears it on sign-out and at login.
  3. `?token=<jwt>`, **deprecated** (see Deprecation).
- **Origin check:** applies to cookie auth only. The `Origin` header must exactly match an entry of `ENZARB_REALTIME_ALLOWED_ORIGINS`, a comma-separated list of `scheme://host[:port]` (http or https, no path; an invalid entry fails startup). When the variable is unset or empty, `Origin` must equal the `Host` header. A missing, `null`, unparsable or mismatching `Origin`: HTTP 403 before the upgrade. Bearer and query auth are not Origin-checked.
- **JWT:** HS256, signed with `ENZARB_REALTIME_JWT_SECRET`, which ui and enzarb-realtime share. Claims: `sub` (GitHub login), `projects` (array of Project names the user can see), `aud: "enzarb-realtime"`, `exp` (≤ 5 min after issue; checked at connect). The ui mints it from a remote function. An invalid or missing token from the selected source: HTTP 401 before the upgrade (Authorization and Origin cases: see Auth sources and Origin check).
- **Expiry:** the server closes the socket at `exp` (never later than 5 min after connect) with close code **4001**; the client fetches a fresh token, reconnects and refetches. The ui refreshes the `enzarb_live` cookie when it fetches the new token.
- **Deprecation:** a `?token=` connection logs a warn "token in query string is deprecated" with an in-process `deprecated_total` field (a log field, not a metric). `?token=` and the ui flag `ENZARB_REALTIME_LEGACY_TOKEN_URL` are removed once that log shows zero uses for 7 days.
- **Frames** (server to client, JSON text; client messages are ignored):
  - `{"topic":"work_item","id":123,"project":"enzarb"}`, sent only to clients whose `projects` contain `project`;
  - `{"topic":"resync"}`, sent to all clients: refetch everything. Sent after the service's LISTEN connection was re-established, when a work item's project could not be resolved, and when a client's bounded buffer overflowed.
- **Keepalive:** ping every 15 s; clients that do not pong are dropped. `GET /healthz` (liveness) and `GET /readyz` (200 only while LISTEN is connected).
- **Database:** the service `LISTEN`s on `work_item_changed` (section 6) and resolves id to project with `SELECT project FROM workflows_api.work_item_v WHERE id = $1`. Runtime role `enzarb_realtime` needs `USAGE` on `workflows_api` and `SELECT` on `workflows_api.work_item_v` only (follow-up: grant in `workflows/` migrations, pgop Role in `helm/`).
- **Routing:** `/live/` to enzarb-realtime:8080 (follow-up in `helm/`).

## 10. GitHub App

- **Permissions:** Issues RW, Pull requests RW, Contents RW, Workflows RW, Checks RW, Commit statuses R, Packages R, Metadata R. Read-write run tokens minted by `mint_clone_credential` (single repo) carry `contents`, `pull_requests` and `workflows` write so agents can edit `.github/workflows`; read tokens omit `workflows` (GitHub has no read level).
- **Deps token (`deps_token`):** the read-only multi-repo token from `mint_read_credential` (same-Project repos) carries `contents: read` and `packages: read`. The sandbox exposes it to the agent process only, as `ENZARB_DEPS_TOKEN` (cargo git deps) and `NODE_AUTH_TOKEN` (`npm ci` against npm.pkg.github.com), never written to disk. The App must be granted **Packages: Read** and each installation must accept it; until then GitHub rejects the request and the connector falls back to `contents: read` with a warning, so `npm ci` of private `@enzarb/*` packages returns 401.
- **Events:** issues, issue_comment, pull_request, pull_request_review, pull_request_review_comment, check_suite, check_run, status, installation, installation_repositories. Existing Apps must be updated for the new permission and events (see [oldie.md](oldie.md)).
- **Webhook URL:** `https://<host>/hooks/github`.
- **Install link and refresh:** `https://github.com/apps/<slug>/installations/new`. At sign-in the UI uses the user-to-server token once (never stored) to snapshot the repositories reachable through installations of this App (`GET /user/installations`, `GET /user/installations/{id}/repositories`) into `app.user_repositories`. `GET /login/github?refresh=1&return=<same-origin path>` re-runs that flow. Set the App's **Setup URL** to `<public>/login/github?refresh=1` with "Redirect on update" enabled so users land back in enzarb after installing.
- **Registration manifest:** `docs/github-app.yml` (setup in `docs/dev.md`). The same App also provides UI login (user authorization): its callback is `<public>/login/github/callback` (`callback_urls` in the manifest) and its Client ID/secret are the UI's `GITHUB_OAUTH_CLIENT_ID`/`GITHUB_OAUTH_CLIENT_SECRET`.

## 11. CI access to private enzarb dependencies (obsolete)

Removed by ADR-0015. With path dependencies inside the monorepo, CI and Docker builds need no deploy keys, ssh agents or build secrets; the `ENZARB_*_DEPLOY_KEY` secrets are no longer used.

## 12. Agent jobs (`workflows/` `engine::machine`)

- **Agent output:** the final message ends with exactly one fenced `json` block `{ "decision": "...", "body": "<markdown>" }`, with nothing after it. The machine reads it from `RunFinished.summary`.
- **Decisions per job kind:**
  - triage: `questions | ready | duplicate`
  - plan: `plan`
  - implement: `done | blocked` (for `done`, `body` is the PR description)
  - review: `approve | request_changes | comment`
  - address_comments: `done | blocked`
  - task: `reply | blocked`
  - A missing or invalid block → `Failed` (retryable).
- **Engine events:**
  - `JobSucceeded {job_id, kind, output}` / `JobFailed {job_id, kind, error}`, where `output` is the `RunFinished` fields (`summary, branch, head_sha, pushed`). Implement requires `pushed: true`.
  - `TimerFired {job_id?}`: with a `job_id` it is a job deadline, otherwise the work item's `wake_at`.
- **Handoff:** `StartWorkflow {key, workflow, event}`. The reducer inserts `event` (a synthesized `ChangeRequestOpened`) with dedupe key `handoff:<event.id>` in the same transaction.
- **Branches:**
  - read-only steps: `enzarb/<step>-<n>`
  - implement: `enzarb/issue-<n>`
  - review and address_comments: the PR's `head_ref`, used as both `base_ref` and `branch`.
- **Prompt templates:** `workflows/crates/engine/prompts/*.md`. Untrusted text is wrapped in `<untrusted>` tags.

### Docker builds

Components with path dependencies (`ui`, `sandbox-proxy`, `sandbox-container`, `workflows`) build with the repo root as context: `docker build -f <dir>/Dockerfile .`. No build secrets are needed (ADR-0015).

## 14. Web Push (UI notifications)

The UI is an installable PWA (`/manifest.webmanifest`, service worker `service-worker.js`) and sends Web Push (VAPID) notifications when a work item newly needs the user. Additive: nothing here changes an existing interface.

- **Tables (`app`, migration `0006_push_subscriptions.sql`).** `app.push_subscriptions(id, owner, endpoint unique, p256dh, auth, categories text[], user_agent, created_at, last_used_at)`: one row per device, `owner` is the GitHub login (no FK). `app.push_sent(owner, work_item_id, category, state_key, sent_at)` with the four key columns as primary key: the sent-log used to de-duplicate across pods. `enzarb_ui` has no privilege on either table.
- **`app_api` functions** (`SECURITY DEFINER`, all taking the owner, which the UI passes from the session login or the Project's `spec.owner`, never from client input; `EXECUTE` granted to `enzarb_ui` only): `push_subscription_upsert(owner, endpoint, p256dh, auth, categories, user_agent) -> boolean` (false and no change when the endpoint belongs to another owner), `push_subscription_list(owner)` (no keys), `push_subscription_targets(owner, category)`, `push_subscription_set_categories(owner, endpoint, categories)`, `push_subscription_delete(owner, endpoint)` (Settings, and pruning after the push service answers 404 or 410), `push_subscription_touch(owner, endpoint)`, `push_claim(owner, work_item_id, category, state_key, window_secs) -> (claimed, recent)` (`recent` counts this claim), `push_claim_release(owner, work_item_id, category, state_key) -> boolean` and `push_sent_prune(older_than_days)`.
- **Categories** are `approval`, `merge`, `blocked`, `failed`: the Work queue's classification (`classifyNeedsYou`, `ui/src/lib/work-items.ts`). Run failures reach the sender as the work item's `Failed` state, so they use `failed`. Only Projects the user owns notify.
- **Trigger and de-duplication.** Every UI pod `LISTEN`s on `work_item_changed` (section 6), batches ids for 500 ms, reads `workflows_api.work_item_v` and `transition_v`, and classifies. It sends only if its `push_claim` insert won: the key is `(owner, work item, category, "<state>:<id of the latest transition into that state>")`, so a pod rollout or a second replica never double-sends, and a later re-entry into the state notifies again. Delivery is at most once per transition across pods, with one exception: if no device accepted the message and none was reported gone (404/410), every send failed transiently, so the claimant releases the claim (`push_claim_release`) and the next update to the item can notify again. A crash between claim and send still drops that notification. Rows older than 30 days are pruned. If more than 3 claims by one user fall within 60 s, the extras collapse into one "N items need you" notification (tag `work-summary`).
- **Payload** (JSON, exactly `title`, `body`, `url`, `tag`): a fixed title per category, the item title truncated to 120 characters as body, the in-app path (`/task/<id>`; the old `/work/<id>` redirects there) as `url` and `work-<id>` as `tag`. Never `state_data`, failure text, tokens, code or logs.
- **Secret.** `enzarb-vapid-key` (data keys `public-key`, `private-key`, base64url), created once by a chart pre-install/pre-upgrade Job running the UI image (`scripts/vapid-secret.ts`) and never replaced; `secrets.vapidKey.existingSecret` names your own. Only the `enzarb-ui` Deployment reads it (optional `secretKeyRef`s, so pods start without it, with notifications off). Changing the keypair invalidates every existing browser subscription.
- **Remote functions** (`ui/src/lib/push.remote.ts`): `getPushState` (public key and the caller's devices), `subscribe`, `updateCategories`, `unsubscribe`, `sendTest` (rate limited to one per 10 s per user per pod). The service worker never caches `/_app/remote`, `/live/`, non-GET requests or navigation responses.

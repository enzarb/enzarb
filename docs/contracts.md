# Cross-component contracts

Interfaces that more than one component depends on. Implementations must match this document. If a change needs a different shape, update this file in the same change (same PR in the `enzarb` monorepo, github.com/enzarb/enzarb) and say so in the PR.

## 1. Library dependencies

All components live in the monorepo (ADR-0015); library dependencies are path dependencies:

```toml
enzarb-proto = { path = "../proto/crates/enzarb-proto" }
enzarb-crds  = { path = "../operator/crates/enzarb-crds" }
```
- A library change and its consumers land in the same PR. Deployed components still roll out independently, so wire and schema changes stay backward compatible.
- `connectors.event_v` / `app_api` view and schema additions (new columns, view fields) must be backward compatible for one release: add, never rename or drop in the same release. Consumers should tolerate a missing new column for one chart version where practical. The main guard is the chart's migration ordering (legacy, connectors, then ui); the second is that a commit releasing several components publishes a single chart version pinning all of them (docs/ci.md "Releases").
- Crate paths:
  - `proto/crates/enzarb-proto`
  - `operator/crates/enzarb-crds`
- TS: `ui/` depends on `@enzarb/proto` via `"@enzarb/proto": "file:../proto"`; no registry is involved.

Shared choices across the Rust components:
- tokio, axum 0.8, tracing + tracing-subscriber (JSON logs), serde, thiserror/anyhow;
- sqlx (postgres, runtime-tokio, tls-rustls), kube + k8s-openapi (latest k8s feature), reqwest (rustls), jsonwebtoken;
- toolchain: pinned in the single `rust-toolchain.toml` at the repo root (one Cargo workspace, one `Cargo.lock`), edition 2024.

## 2. `Project` CRD (`enzarb.dev/v1alpha1`, **cluster-scoped**)

Types are in the `enzarb-crds` crate; the CRD YAML is generated by `cargo run -p enzarb-crds --bin crdgen`.

```yaml
apiVersion: enzarb.dev/v1alpha1
kind: Project
metadata: { name: enzarb }            # DNS label, max 50 chars ("sb-<name>-workspace" ≤ 63)
spec:
  owner: ruckc                         # owner id (GitHub login of the creator)
  displayName: enzarb
  repositories:
    - url: https://github.com/enzarb/enzarb-ui    # canonical https URL
      connector: github
      defaultBranch: main
  runMode: worktree                    # worktree | fresh; accepted, currently unused
  triggers: { issues: true, changeRequests: true, mentions: true }   # accepted, currently unused
  sandbox:
    image: ""                          # empty = operator default (--sandbox-image)
    storage: 20Gi
    resources: {}                      # core/v1 ResourceRequirements
status:
  observedGeneration: 3
  namespace: enzarb-sandboxes          # the shared sandbox namespace (ADR-0013)
  sandbox:
    name: sb-enzarb                    # Sandbox CR name in that namespace: "sb-<project>"
    endpoint: ws://sb-enzarb.enzarb-sandboxes.svc:7070/v1/mux
    authSecretRef: { name: sb-enzarb-auth, key: token }   # in status.namespace
  conditions:                          # metav1.Condition, ordered for the UI checklist
    - type: ResourcesReady             # auth Secret, workspace + docker PVCs, NetworkPolicy
    - type: SandboxReady
    - type: Ready
```

Conditions: a failed step is `status: False` with a `reason` ending in `Failed`, `Failure` or `Error` (e.g. `NotOwnedError`: an object with the Project's name exists but has no owner), or the named terminal reason `InvalidSpec` (reported on `ResourcesReady`, for an invalid Project name and for a repository that another Project already owns, see "One Project per repository" below). Any other `False` reason is shown as in progress (e.g. `Terminating`: a deleted Project's objects with the same name are still being removed).

Objects per Project (ADR-0013), all in the shared namespace and labelled `enzarb.dev/project=<name>`: Sandbox `sb-<name>` (its pod and headless Service share the name; the Service is owned by the Sandbox), Secret `sb-<name>-auth`, PVCs `sb-<name>-workspace` and `sb-<name>-docker`, NetworkPolicy `sb-<name>`, each with a controller ownerReference to the Project. Names are at most 50 characters, enforced by a CEL rule in the CRD, the operator and the UI. Sandbox pods run as ServiceAccount `enzarb-sandbox` with no token and no RBAC: **no Kubernetes API access**; any future access is limited to other namespaces. Consumers find the sandbox only through `status.namespace` and `status.sandbox` (no derived fallback).

Defaults: `runMode: worktree`, all `triggers` true, `sandbox.storage: 20Gi`. Helpers in `enzarb-crds`: per-Project object names (`sandbox_name()`, `auth_secret_name()`, `workspace_pvc_name()`, `docker_pvc_name()`), `matches_repo()`, `RepoKey::from_url` / `RepoKey::from_connector_url` (github.com only for now; lowercases).

Resources and pod-shape changes: `spec.sandbox.cpu` (integer 1-64) and `spec.sandbox.memory` (`<int>Mi|Gi`, 512Mi-256Gi) set the sandbox container limits; the operator derives requests at 25% (floors 100m / 256Mi), and explicit `spec.sandbox.resources` win per key. Unset injects nothing. Any change to the desired pod shape (image, `ENZARB_*` env incl. `spec.maxRuns`, sandbox and dockerd resources, runtime class, mounts) is **queued, not applied**: the operator publishes `status.pendingChange {generation, since, deadline, reason}` (`deadline` = `since` + the drain timeout, optional, additive; the UI shows the remaining time next to "Roll now") and the informational condition `SandboxChangePending` (replaces `SandboxImageRoll`; no effect on `Ready`) and leaves the pod alone. The annotation `enzarb.dev/drained-generation` set to the `generation` of the pending change is an ack that releases the operator to delete the pod (never the Sandbox or PVCs); it currently has no producer, and only an exact match counts. A newer spec change bumps `generation`, so an older ack no longer applies. The owner can also release the roll from the UI ("Roll now"): the UI sets the Project annotation `enzarb.dev/roll-now-generation` to the `generation` the user saw (owner-only, refused with 409 if the pending generation has moved on); the operator treats an exact match like an ack, and a newer change needs a fresh click (ADR-0023). Without either the operator applies the change after `--sandbox-roll-drain-timeout` (default 30m) from `since`. `pendingChange` is removed once the recreated pod matches. When the operator deletes the pod it records `status.lastRoll {at, since, reason, image}` (`since` = the change's `pendingChange.since`, so the drain wait is `at - since`; `image` = the sandbox image the new pod runs). It is additive, kept until a newer roll replaces it, and used by the UI for the "sandbox applied" stage of merge-to-deployed (ADR-0025). Storage growth is not queued (the PVC expands in place).

Repo key: a repository's **repo key** is `<connector>:<owner>/<repo>`, e.g. `github:enzarb/enzarb-ui`, always lowercase. The UI shows a delivery in a Project's Events tab by matching the event's `repo` (`owner/repo`, lowercase) against the Projects' `spec.repositories`.

One Project per repository: a repo key (`RepoKey::from_connector_url`, compared case-insensitively) belongs to at most one Project. When several Projects list it, the oldest by `(metadata.creationTimestamp, name)` wins; `name` breaks timestamp ties and is unique because the CRD is cluster-scoped. Every other Project has `ResourcesReady=False` with the terminal reason `InvalidSpec`, like an invalid name; its message names the repository only, never the winning Project. The winner is the Project that shows the repository's events.

Renaming: the owner may change `spec.displayName` (UI `setDisplayName`; owner-only, trimmed, non-empty, at most 100 characters). `metadata.name` is immutable. No sandbox restart: the display name is not part of the pod.

Changing repositories: the owner may replace `spec.repositories` after creation (UI `setRepositories`; same key-only, live-access-check and one-Project-per-repository rules as creation; a repository already in the Project may be kept or removed without being checked or listed, so archived repositories can be dropped). It takes effect without a sandbox restart and without drain-first (`status.pendingChange` is not used): repositories are not part of the sandbox pod. The Events tab and the `repos` claim of the realtime token follow the new list; the sandbox clones a repository when a step or chat first needs it. Clones of removed repositories stay on the workspace volume until the Project is deleted.

## 3. sandbox-init

**Mux endpoint:** `ws://<pod>:7070/v1/mux`. Clients must send `Authorization: Bearer <token>`. The token is the `token` key of the Secret named in `status.sandbox.authSecretRef` (`sb-<project>-auth`) in `status.namespace`; the operator generates it, and it is mounted in the sandbox at `/var/run/enzarb/auth/token`.
- Allowed clients: `sandbox-proxy`.
- Health: `GET :7070/healthz`. Body is JSON `{"status":"ok","dockerd":{"state":"starting|running|failed|stopped|disabled", ...}}`, always HTTP 200 (readiness never depends on Docker). `dockerd` is absent when the supervisor is not wired.

**Docker (ADR-0012, sidecar superseded by ADR-0016):** always on. The operator sets the pod `runtimeClassName` (`gvisor`) cluster-wide via `--sandbox-runtime-class`. Sandbox pod layout:
- One container, `sandbox`. No `dockerd` sidecar and no `docker-sock` volume.
- sandbox-init (pid 1) runs and supervises `dockerd` as root and drops everything else it spawns to uid/gid 1000 with no-new-privs. The `sandbox` container's `securityContext` overrides the pod-level non-root settings: `runAsUser: 0`, `runAsNonRoot: false`, `privileged: false`, `allowPrivilegeEscalation: true`, `drop: [ALL]` plus the gVisor Docker capability set (includes `SYS_ADMIN`, `NET_ADMIN`, `NET_RAW`, `SETUID`, `SETGID`, `CHOWN`). The pod-level `runAsUser`/`runAsGroup`/`fsGroup` (1000) stay. The kata profile is `privileged: true`.
- Volumes: `workspace` (PVC) at `/workspace`, `auth` (Secret) at `/var/run/enzarb/auth`, `docker-data` (PVC `sb-<name>-docker`) at `/var/lib/docker`.
- Env: `DOCKER_HOST=unix:///var/run/docker.sock` (group 1000, mode 0660), `ENZARB_DOCKERD_ARGS` (the runtime profile's dockerd flags). Optional sandbox-init env: `ENZARB_DOCKERD` (`off` disables), `ENZARB_DOCKERD_BIN`, `ENZARB_DOCKERD_SOCKET`, `ENZARB_DOCKERD_DATA_ROOT`, `ENZARB_DOCKERD_EXEC_ROOT`; pruning: `ENZARB_DOCKER_PRUNE` (`off` disables), `ENZARB_DOCKER_PRUNE_AGE` (default `24h`), `ENZARB_DOCKER_PRUNE_MIN_FREE` (default 15%), `ENZARB_DOCKER_BIN`; workspace build caches: `ENZARB_WORKSPACE_PRUNE` (`off` disables), `ENZARB_WORKSPACE_PRUNE_MIN_FREE` (default 20%).
- The image ships `dockerd`, `containerd`, `runc` and the `docker` CLI plus the buildx and compose plugins. Inner containers and builds default to `--network=host` through the image's `docker` wrapper (dockerd runs with `--iptables=false`); use `--user 1000:1000` so bind-mounted files stay editable.

**PTY channels:** CLOSE reason is `exit:<code>` or `signal:<n>`. A client half-close leaves the process running.

**Config (env):**
- Core: `ENZARB_LISTEN` (default `0.0.0.0:7070`), `ENZARB_AUTH_TOKEN_FILE`, `ENZARB_WORKSPACE` (`/workspace`), `ENZARB_SHELL`, `ENZARB_GRACE_SECS` (25; the pod's `terminationGracePeriodSeconds` must be larger).
- Git: `ENZARB_NET_RETRY_DELAYS_MS` (`10000,30000`: pauses before retrying a clone/fetch/push that failed on a transient network error; auth failures and rejected pushes are never retried), `ENZARB_PUSH_ATTEMPT_SECS` (120: wall-clock cap of one push attempt), `ENZARB_FETCH_ATTEMPT_SECS` (180: wall-clock cap of one clone/fetch attempt, so a dead host fails early; a timeout counts as transient and is retried; raise it for very large repos), `ENZARB_GIT_NAME`, `ENZARB_GIT_EMAIL`, `ENZARB_CLAUDE_TOKEN_FILE` (legacy only: the per-Project legacy file, read when `claude_token` is absent; removed with the fallback).
- Agent: `ENZARB_CHAT_AGENT` (`ez` default | `claude`; other values fail startup; ADR-0028), `ENZARB_ACP_AGENT_BIN` (the chat agent binary: default `ez`, run as `ez acp`; `claude-agent-acp` for the claude agent), `ENZARB_CHAT_RUNTIME_TOOL` (mise tool providing the binary when it is not installed: empty for ez, `npm:@agentclientprotocol/claude-agent-acp` for claude), `ENZARB_CHAT_MODEL` (empty: the adapter's default; the model of the `claude` profile sandbox-init writes for ez), `ENZARB_CANCEL_GRACE_SECS` (10). `ENZARB_PERMISSION_POLICY` is accepted and ignored (deprecated 2026-10-15: there is no permission policy, ADR-0011 amendment).
- Chat (ADR-0014; sandbox-init config only, no Project spec field): `ENZARB_MAX_CHATS` (1; `0` disables chat and removes `acp` from `welcome.features`), `ENZARB_CHAT_IDLE_SECS` (1800), `ENZARB_CHAT_MAX_SECS` (28800), `ENZARB_CHAT_RETENTION_DAYS` (7).
- Chat permission mode (claude agent only; ADR-0014 amendment 2026-10-12 (2); sandbox-init config only): `ENZARB_CHAT_PERMISSION_MODE` (`bypassPermissions` default | `default` | `plan`; other values fail startup; defaults to `default` when bypass is not allowed) and `ENZARB_CHAT_ALLOW_BYPASS` (true; `false` makes bypass unavailable, and `false` with an explicit bypass mode fails startup). Browser-bound `_enzarb/mode {sessionId, modeId, bypassAllowed}` is sent after session establishment and after each successful `session/set_mode`. The `session/set_mode` allowlist is {`bypassPermissions` (only while allowed), `default`, `plan`}. In bypass the agent sends no `session/request_permission` for ordinary tool calls.

**Agent sessions (ACP, ADR-0011):** generic sandbox primitives (the `step_*` frames, [protocol.md](../proto/docs/protocol.md)); no orchestrator drives them at the moment ([ADR-0027](adr/0027-workflow-clean-slate.md)).
- sandbox-init is an ACP client of `@agentclientprotocol/claude-agent-acp`, one agent process per step, with cwd set to the workspace and `CLAUDE_CODE_OAUTH_TOKEN` in its environment.
- **Protocol steps:** `initialize`, then `session/new` (mode `default`), then `session/prompt`.
- **Permissions:** every `session/request_permission` is allowed (`allow_always` if offered, else `allow_once`; `cancelled` when the request has no allow option) and recorded as a `permission` transcript record with `decision: "allow"`, `rule: "sandbox"`. There are no command allow-lists or deny-lists: the sandbox (gVisor, the Project's egress NetworkPolicy, no Kubernetes API access, scoped tokens) is the security boundary (ADR-0011 amendment 2026-10-15).
- **Cancel:** `session/cancel`, then a grace period, then the process group is killed.
- **Continuation (steps with a `result_schema`):** when a turn ends (`end_turn`) without a valid `submit_result`, sandbox-init continues the same ACP session with a fixed user turn (wait in the foreground for background work, then `submit_result` or report blocked), recorded as a `user` session event. It repeats while the previous turn made at least one `tool_call`/`tool_call_update`; a turn with no tool calls and no result ends the step as before (`success`, no result). There is no count or time limit; cancel/stop ends it. It is one step: one session, one `step_finished`, with usage summed over all turns.

**Interactive chat (ACP, ADR-0014; [design](design/chat-tab.md)):**
- **ez chats (default, ADR-0028).** sandbox-init runs `ez acp` with `EZ_CONFIG_DIR=<ws>/.enzarb/ez-config` (a `config.toml` it writes: `default_profile = "claude"`, provider `claude-code`, model `ENZARB_CHAT_MODEL`) and `EZ_SESSIONS_DIR=<ws>/.enzarb/chats/<chat_id>/ez-sessions` (transcripts outside the worktree). Modes are ez's (the chat worktree's `.ez/modes.toml`, else ez's built-in mode): `session/set_mode` accepts exactly the ids of the agent's `modes.availableModes`, no starting mode is enforced, and `_enzarb/mode` carries the active ez mode id with `bypassAllowed: false`. `initialize` always advertises `clientCapabilities._meta.ez.askUserQuestion: true` to ez; agent-sent `_ez/ask_user_question {sessionId, questions:[{question, header, multiSelect, options:[{label, description}]}]}` is forwarded to the browser only when the browser's `initialize` advertised the same capability (otherwise sandbox-init answers `{answers: [], cancelled: true}`). The browser answers `{answers:[{question, selected:[label…], other: string|null}], cancelled}`; sandbox-init rebuilds it from the question's own labels, and anything invalid (unknown or duplicate label, several answers to a single-select question, a missing question, `other` over 4 KiB, an error) becomes `cancelled`. Pending questions are cancelled with permissions (close, idle, `session/cancel`). `session/new`/`load` carry no `_meta`. Everything below applies to ez chats as well, except the claude-specific `_meta` and mode rules.
- One `acp` mux channel is one agent child (`ez acp` or `claude-agent-acp`), in its own process group. DATA_BIN carries newline-delimited JSON-RPC (max line 4 MiB). sandbox-init is a filtering relay: it forces `clientCapabilities` to none, `cwd` to the chat worktree and `mcpServers` to `[]`, allows only `initialize`, `session/new`, `session/load` (registered sessions only), `session/prompt`, `session/cancel` and `session/set_mode` (`default` or `plan`), and redacts the Claude token.
- **Permissions:** sandbox-init allows every `session/request_permission` itself (`allow_always` if offered, else `allow_once`), recorded with `decision: "allow"`, `rule: "sandbox"`; the browser never sees it. Only leaving plan mode (`toolCall.kind == "switch_mode"`) goes to the user; there only `allow_once`, `reject_once` or `cancelled` answers are accepted, and anything else becomes `reject_once`. `_enzarb/permission_denied` and the `_meta.enzarb` hint are no longer sent (consumers must tolerate their absence).
- **Environment:** the Claude token only. A chat never receives a clone, deps or npm token, so it cannot push or install private packages.
- **Limits:** at `ENZARB_MAX_CHATS` a new open closes the existing chat with `superseded`; 1 `acp` channel per socket; prompts up to 256 KiB. Chat does not block drain.
- **CLOSE reasons on an `acp` channel:** `idle`, `superseded`, `shutdown` (sandbox-init got SIGTERM), `limit` (hard lifetime or line cap), `exit:<n>`, `signal:<n>`.

**Image build:** `docker buildx build -f sandbox-container/Dockerfile --load .` from the repo root (path dependency on `proto/`). The minimal runtime image (ADR-0012, enzarb-sandbox-container#16) contains:
- sandbox-init;
- ez (`/usr/local/bin/ez`, the chat agent);
- node 24 + claude-agent-acp + the glibc `claude` binary (ez's claude-code driver, and claude chats);
- mise;
- build-essential, pkg-config, libssl-dev;
- git, ca-certificates, openssh-client.

Plus curl (mise's Rust backend needs it for rustup) and Docker 29.8.2 (static bundle: `dockerd`, `containerd`, `runc`, the `docker` CLI, with the buildx and compose plugins; ADR-0016). No Rust, npm or extra CLI tools.

**Toolchains (mise, per project, persisted on the PVC):**
- `MISE_DATA_DIR=/workspace/.toolchains/mise`, `MISE_CACHE_DIR=/workspace/.toolchains/cache`, `CARGO_HOME=/workspace/.toolchains/cargo`, `RUSTUP_HOME=/workspace/.toolchains/rustup`.
- `MISE_TRUSTED_CONFIG_PATHS=/workspace`, `MISE_YES=1`, `MISE_IDIOMATIC_VERSION_FILE_ENABLE_TOOLS=rust`.
- `PATH` includes the mise shims, so a repo's `mise.toml` or `rust-toolchain.toml` determines its tools.

**Filesystem (on the PVC):**
- `/workspace`: repos and worktrees.
- `/workspace/.toolchains/`: mise data and cache, cargo, rustup.
- `/workspace/repos/<slug>-<hash>/`: one clone per repo URL.
- `/workspace/tasks/<task_id>/<owner>/<repo>`: a step's workspace (`task_id` is the opaque id in `step_start`).
- `/workspace/worktrees/chat-<chat_id>/`: a chat's worktree (`chat_id` is 16 random hex chars), detached at `origin/<default branch>` of the chosen clone; commits go on the local branch `enzarb/chat-<chat_id>`. A sweep removes chat worktrees with no live channel and no activity for `ENZARB_CHAT_RETENTION_DAYS`.
- `/workspace/.enzarb/chats/<chat_id>/`: `meta.json` (`acp_session_id`, `repo`, `worktree`, `created`, `last_active`) and `transcript.jsonl` (0600; `log`, `acp`, `update`, `permission`, `prompt` records).
- `/workspace/.enzarb/chat-home/.claude`: `CLAUDE_CONFIG_DIR` for chat agents, so `session/load` survives pod restarts.
- `/workspace/.enzarb/claude-token`: mode 0600. Legacy per-Project token, read only while `claude_token` is absent from `open`. On connect sandbox-init promotes it with `credential_captured{legacy:true}` (first Project wins), then deletes it when the proxy answers `credential_state{configured:true}`. New captures are never written to disk.

## 4. proto messages

The wire format (frame layout, flow control) and the step frames are defined in `proto/docs/protocol.md`. Frame types: `CTRL, DATA_BIN, DATA_JSON, WINDOW, CLOSE`.

CTRL payloads are JSON objects tagged by `"type"` and use channel 0:

| Message | Direction | Fields |
|---|---|---|
| `hello` | client → server | `versions: [1]`, `client: "ui" \| "proxy" \| "executor"` |
| `welcome` | server → client | `version`, `features?: [string]` (optional; `"acp"` when chat is enabled, `"steps"`, `"ez_steps"` (agent steps may carry `mode` and `ez`, ADR-0029; implies `"steps"`), `"stats"`, `"file_read"`, `"file_read_chat"`; absent means none) |
| `open` | client → server | `channel`, `kind: "pty" \| "acp"`, `cols`, `rows`, `command?: [..]`, `repo?`, `resume?`, `claude_token?` (acp only; set by the proxy) (see below) |
| `opened` / `open_error` | server → client | `channel` / `channel, message, code?` |
| `resize` | client → server | `channel`, `cols`, `rows` |
| `step_start` (ez fields gated by `ez_steps`), `step_accepted`, `step_status`, `step_state`, `step_steer`, `step_stop`, `step_resume`, `session_event`, `step_finished` | both | Generic step/session primitives, gated by `welcome.features` `steps`; fields in `proto/docs/protocol.md`. No orchestrator drives them at the moment ([ADR-0027](adr/0027-workflow-clean-slate.md)); the proxy does not relay them to browsers |
| `credential_captured` | server → client | `kind: "claude_oauth"`, `token?` (the captured token; **proxy-only**: the proxy consumes the frame, encrypts and stores the token in Postgres, never forwards it to the browser and never logs it), `legacy?: bool` (a promoted legacy file: store only if the user has no token) |
| `credential_status` | client → server | (none); browsers may send it |
| `credential_state` | server → client | `kind: "claude_oauth"`, `configured: bool`, `scope?: "user"` (the Claude token is per user, ADR-0004 amendment 2026-10-13). The proxy also sends it to the sandbox as the answer to a `legacy` capture |
| `stats_request` | client → server | (none); only after `"stats"` is in `welcome.features` (an old server ignores it) |
| `stats` | server → client | reply to `stats_request`: `ts_ms` (unix ms, always present) plus raw values, each omitted when it could not be read (absent = unknown, never 0): `cpu_usage_usec`, `cpu_user_usec`, `cpu_system_usec` (cgroup v2 `cpu.stat`), `memory_bytes` (`memory.current`, a gauge), `memory_limit_bytes` (`memory.max`; omitted when the cgroup is unlimited), `memory_inactive_file_bytes` (`memory.stat` `inactive_file`), `io_read_bytes`, `io_write_bytes` (`io.stat` `rbytes`/`wbytes` summed over devices), `storage_used_bytes`, `storage_total_bytes` (statvfs of the workspace). CPU and IO values are cumulative; consumers compute rates. Read on demand only: no sampling, no push; nothing polls it at the moment |
| `file_read` | client → server | `id` (client-chosen correlation string), `path` (absolute under `/workspace`, or relative: to the worktree `/workspace/worktrees/chat-<chat_id>` of the chat open on the same mux session when `"file_read_chat"` is in `welcome.features`, else to `/workspace`; the result must still be under `/workspace`); only after `"file_read"` is in `welcome.features`. Browsers may send it (the proxy forwards `"file_read"` only when the sandbox advertises it) |
| `file` | server → client | reply to `file_read`: `id`, `path` (as requested), and either `content` (UTF-8 text) or `code` + `message`. `code`: `not_found`, `outside_workspace` (the path, after resolving `..` and symlinks, is not under `/workspace`), `not_a_file`, `too_large` (more than 131072 bytes), `not_utf8`, `io`; clients tolerate other values. Additive, protocol version stays 1 |
| `credential_clear` | client → server | `kind: "claude_oauth"`; browsers may send it (on the proxy's allowlist). The proxy handles it locally by deleting the owner's row (`claude_credential_delete`) and answers `credential_state{configured:false, scope:"user"}`; it is not forwarded to the sandbox |
| `error` | both | `code`, `message`, `run_id?`, `channel?` (a `run_id` routes the error to that step's pending request) |

**Claude token (per user, ADR-0004 amendment 2026-10-13):** one encrypted row per user in Postgres (`app.claude_credentials`, see [database.md](database.md)), keyed by the authenticated `spec.owner`, never by frame content. No Kubernetes Secret holds it, and the sandbox keeps no copy on disk. The proxy is the only writer of put, rekey and sandbox-initiated clear (it consumes `credential_captured`, and handles `credential_clear`); the UI may delete only its own row, through `app_api.claude_credential_delete_own(owner)` (the owner is the session login), so Remove needs no running sandbox. The ciphertext is readable only by the proxy, and the UI sees presence and `updated_at` only (`app_api.claude_credential_v`). Delivery is additive in proto (protocol version stays 1; old decoders ignore the fields):
- **Chats:** `open{kind:"acp"}` gains `claude_token` (optional), set **only by the proxy** when it forwards the browser's `open` to the sandbox. The proxy drops any browser-supplied value, and answers the browser with `open_error{code:"no_credential"}` itself when the owner has no row. sandbox-init puts it in the chat child's environment only.
- **Fallback during rollout:** the sandbox image rolls out first (ADR-0004 Rollout order), before the proxy enforces `no_credential`, so legacy files are promoted before enforcement. Until removal, when `claude_token` is absent sandbox-init still reads the legacy `/workspace/.enzarb/claude-token` if present; otherwise it answers `no_credential`. The fallback is removed once every sandbox runs the new image and the proxy has logged no `legacy` capture for 7 days.
- **Logging:** Debug and tracing output of the `open` frame and of `claude_credential_get` results (proxy) redacts `claude_token`, as `RunStart` debug output does. `credential_captured.token` is never logged either.

**`acp` channels (ADR-0014; additive, protocol version stays 1):**
- `kind: "acp"` opens a byte stream of newline-delimited JSON-RPC (ACP) in DATA_BIN; messages may span frames. `cols`/`rows` are ignored (clients send `0`). `repo` (optional) names a Project repo URL that must already be cloned; `resume` (optional) is the ACP session id, informational only.
- **`welcome.features`:** the sandbox sends `["acp"]` when `ENZARB_MAX_CHATS > 0`. The proxy answers the browser's `hello` itself and forwards the sandbox's features intersected with those it can guard. Decoders ignore unknown fields.
- **Compatibility rule:** a sender must not send `open{kind:"acp"}` before seeing `"acp"` in `welcome.features`. A proxy that cannot decode a frame closes the socket with 1008, so an `acp` open to an old proxy would kill the connection.
- **`open_error.code`** (optional): `chat_disabled`, `chat_limit`, `no_credential`, `repo_not_cloned`, `unsupported_kind`. Clients must tolerate other values. An unknown `kind` decodes (Rust `ChannelKind::Unknown`) and yields `unsupported_kind`.
- **CLOSE reasons** on an `acp` channel: `idle`, `superseded`, `shutdown`, `limit`, `exit:<n>`, `signal:<n>`. Clients must tolerate other text.

- **Wire details** (`proto/docs/protocol.md` and the `enzarb_proto::Ctrl` enum are the source of truth):
  - 10-byte big-endian header: type, flags (0), channel u32, length u32. Max payload 1 MiB, one frame per websocket binary message.
  - 256 KiB initial window per channel and direction. `CLOSE` is a half-close.
  - Optional fields are omitted when absent; `null` is accepted on decode.
- **`usage`** (`enzarb_proto::Usage`, optional on `step_finished`; additive, old decoders ignore it and old senders omit it): `{input_tokens?, output_tokens?, cache_read_input_tokens?, cache_creation_input_tokens?, models?: [string], cost_usd?}`. A field the agent did not report is **absent**, never 0. `cost_usd` is the cost as reported by Claude (`total_cost_usd`, or the `cost` of ACP `usage_update`), even on a subscription token; nothing computes or estimates it.
- **`environment`** (`enzarb_proto::StepEnvironment`, optional on `step_finished`): `{kind, detail}` when a step failed because of its environment rather than the code; `kind` is `disk_full`, `oom`, `toolchain_missing`, `network`, `load` or `unknown` (a kind the consumer does not know; decode-only). Decoders never reject a `step_finished` for an unrecognised `kind`.

## 6. Event log (`connectors.event_v`, Postgres, owned by `connectors/`)

The connectors receiver logs every webhook delivery in `connectors.events`; other components read only the view:

```sql
connectors.event_v(id bigint, source text, delivery_id text, event text, action text,
                   repo text, sender text, payload jsonb, received_at timestamptz)
```
- `repo` is the lowercase `owner/repo` of `repository.full_name`, NULL when the payload names no repository (ping, installation). `(source, delivery_id)` is unique, so a redelivery is not logged twice.
- View columns are append-only; consumers select by name.
- **NOTIFY channel:** `connector_event` (payload: the new event id), sent by the receiver in the insert transaction; not sent for a redelivery.
- **Grants:** `enzarb_ui` and `enzarb_realtime` get `USAGE` on schema `connectors` and `SELECT` on `connectors.event_v`; `enzarb_connectors` reads and writes the table.
- **Reader added:** `enzarb_tracks` also gets `USAGE` on schema `connectors` and `SELECT` on `connectors.event_v` (migration `20261030000001_tracks_grant.sql`; skipped where the role does not exist).
- The legacy schemas `workflows`, `workflows_api`, `engine`, `engine_api` are dropped by the chart's first migration Job.

## 6a. Tracks schema (`tracks`, Postgres, owned by `tracks/`)

Owner role `enzarb_tracks_owner` (pgop schema `tracks`), runtime role `enzarb_tracks`; migrations are embedded in the `enzarb-tracks` image (`enzarb-tracks migrate`) and run by the chart's migration Job after `connectors` and `ui` (history in `tracks._sqlx_migrations`). Nothing outside tracks reads these tables: the ui goes through the tracks API (`GET /v1/decisions`). Changes are additive.

| Table | Holds |
|---|---|
| `tracks.event_decisions` | One row per routed connector event (PK `event_id`, which makes routing at-most-once): `repo`, `project` (NULL when none owns the repo), `sha` (default-branch head the files were read at), `outcome` (`started`, `no_match`, `skipped`, `error`), `matched` (ids of the workflows that started a run), `reasons` (`[{workflow, matched, on, reason}]` for every workflow: the `on` / `if` evaluation), `errors` (invalid file, missing project, GitHub errors), `event_received_at`, `decided_at` |
| `tracks.router_state` | Single row: `floor`, the highest event id when tracks first ran. Events at or below it are history and are never routed |
| `tracks.runs` | A workflow run (ADR-0029 section 5): `id` (uuid), `workflow`, `project`, `repo`, `subject_key` (`owner/repo#number`), `subject`, `event_id`, `sha` (pinned), `status` (`pending`, `running`, `waiting`, `done`, `failed`, `cancelled`), `test`, `current_node`, `visits`, `state` (ez-workflow `RunState`), `reason`, timestamps. Unique on `(event_id, workflow, test)`. Routing only inserts `pending` rows; nothing executes them yet |
| `tracks.node_runs` | One row per node visit (`run_id`, `node`, `visit`, `inputs`, `outputs`, `usage`, `error`, timestamps); written by run execution (rollout step 4) |

**Routing.** tracks `LISTEN`s on `connector_event` (section 6), reads the event from `connectors.event_v`, finds the Project whose `spec.repositories` lists the repo (read-only `get`/`list` on Project CRs; several: the first by name), reads `.ez/workflows.toml` and `.ez/modes.toml` at the head of the repository's `defaultBranch` through the GitHub App (installation token scoped to the repo, `contents: read`), evaluates every workflow's `on` / `if` with `ez-workflow`, and in one transaction writes the decision and a `pending` run per matching workflow. A subject (`owner/repo#number`) with a live run of the same workflow starts no second one (the reason says so). A sweep (at start, after every reconnect, every `ENZARB_TRACKS_SWEEP_SECS`) decides events past the floor that have no decision, so events missed while down are caught up; transient failures (GitHub 5xx, API server) are retried, up to 5 attempts, then recorded as an `error` decision.

## 7. Browser → proxy

- **URL:** `wss://<host>/sandbox/v1/projects/<project>/mux?token=<jwt>`. Browsers can't set headers on websockets.
- **JWT:** HS256, signed with `ENZARB_SESSION_JWT_SECRET`, which ui and proxy share. Claims: `sub` (GitHub login), `project`, `aud: "enzarb-sandbox-proxy"`, `exp` (≤ 5 min after issue; it is checked only at connect).
- **Chat:** uses the same URL, token and authorization. The proxy's CTRL allowlist additionally admits `open{kind:"acp"}` and `credential_clear` (still not `step_*`), relays `acp` DATA byte for byte, and forwards `welcome.features` as described in section 4. `PROXY_IDLE_TIMEOUT_SECS` must be at least `ENZARB_CHAT_IDLE_SECS` (default 2100 s, 35 min).
- **Claude token (ADR-0004 amendment 2026-10-13):** the proxy needs a Postgres role (`enzarb_sandbox_proxy`) and the keyring Secret `enzarb-claude-key`, but **no new Secret RBAC** in `enzarb-sandboxes` (ADR-0013 unchanged). On the mux connection it strips browser-supplied `claude_token`, injects the owner's on `acp` opens, consumes `credential_captured` and handles `credential_clear` itself.
- **Proxy authorization:** the proxy checks that `sub` is the Project's `spec.owner`, resolves `status.sandbox.endpoint` and the auth Secret, and dials sandbox-init with `client: "proxy"`.

### 7a. Browser realtime stream (enzarb-realtime)

- **URL:** `wss://<host>/live/v1/stream`, no query string.
- **Auth sources**, in precedence order; the first source present wins:
  1. `Authorization: Bearer <jwt>`, for non-browser clients. A present `Authorization` header is authoritative: if it is not `Bearer <non-empty>` (scheme case-insensitive), the result is HTTP 401 with no fall-through to the cookie or the query string.
  2. Cookie `enzarb_live`, for browsers: `Set-Cookie: enzarb_live=<jwt>; HttpOnly; Secure; SameSite=Strict; Path=/live/; Max-Age=300`, with no `Domain`. `Max-Age` equals the token's 5 min `exp` TTL (both from one clock read), so the cookie never outlives the token. The ui sets it from the signed-in session and clears it on sign-out and at login.
  3. `?token=<jwt>`, **deprecated** (see Deprecation).
- **Origin check:** applies to cookie auth only. The `Origin` header must exactly match an entry of `ENZARB_REALTIME_ALLOWED_ORIGINS`, a comma-separated list of `scheme://host[:port]` (http or https, no path; an invalid entry fails startup). When the variable is unset or empty, `Origin` must equal the `Host` header. A missing, `null`, unparsable or mismatching `Origin`: HTTP 403 before the upgrade. Bearer and query auth are not Origin-checked.
- **JWT:** HS256, signed with `ENZARB_REALTIME_JWT_SECRET`, which ui and enzarb-realtime share. Claims: `sub` (GitHub login), `repos` (array of lowercase `owner/repo` keys of the repositories of the Projects the user can see), `projects` (array of Project names; accepted, not used for filtering), `aud: "enzarb-realtime"`, `exp` (≤ 5 min after issue; checked at connect). The ui mints it from a remote function. An invalid or missing token from the selected source: HTTP 401 before the upgrade (Authorization and Origin cases: see Auth sources and Origin check).
- **Expiry:** the server closes the socket at `exp` (never later than 5 min after connect) with close code **4001**; the client fetches a fresh token, reconnects and refetches. The ui refreshes the `enzarb_live` cookie when it fetches the new token.
- **Deprecation:** a `?token=` connection logs a warn "token in query string is deprecated" with an in-process `deprecated_total` field (a log field, not a metric). `?token=` and the ui flag `ENZARB_REALTIME_LEGACY_TOKEN_URL` are removed once that log shows zero uses for 7 days.
- **Frames** (server to client, JSON text; client messages are ignored):
  - `{"topic":"event","id":123,"repo":"enzarb/enzarb"}`, sent only to clients whose `repos` contain `repo`;
  - `{"topic":"resync"}`, sent to all clients: refetch everything. Sent after the service's LISTEN connection was re-established, when an event's repository could not be resolved (lookup failed, no row, or the delivery names no repository), and when a client's bounded buffer overflowed.
- **Keepalive:** ping every 15 s; clients that do not pong are dropped. `GET /healthz` (liveness) and `GET /readyz` (200 only while LISTEN is connected).
- **Database:** the service `LISTEN`s on `connector_event` (section 6) and resolves the id to a repository with `SELECT repo FROM connectors.event_v WHERE id = $1`. Runtime role `enzarb_realtime` needs `USAGE` on `connectors` and `SELECT` on `connectors.event_v` only (granted by the connectors migration).
- **Routing:** `/live/` to enzarb-realtime:8080 (follow-up in `helm/`).

## 10. GitHub App

- **Permissions and events:** as in `docs/github-app.yml` (Issues, Pull requests, Contents and Checks RW; Actions, Deployments, Packages, Commit statuses and Metadata R). The UI uses the App for login, the repository picker and the About page; the receiver only verifies webhooks and logs whatever the App delivers.
- **Webhook URL:** `https://<host>/hooks/github`, signed with `GITHUB_WEBHOOK_SECRET` (`X-Hub-Signature-256`).
- **Install link and repository list:** `https://github.com/apps/<slug>/installations/new`. The UI reads the repositories a user may put in a Project live, with the App's own credentials (no user token is stored or used for it): `GET /app/installations` (App JWT; suspended installations skipped), then `GET /installation/repositories` per installation (installation token, paginated), keeping non-archived repositories where `GET /repos/{o}/{r}/collaborators/{login}/permission` gives `write`, `maintain` or `admin` (bounded concurrency). The list is cached per user in memory for about 60 s, for display only; the pickers' **Refresh repositories** button bypasses that cache. Authorization never reads the list: when a repository is added to a Project (`createProjects`, `setRepositories`) the UI checks that repository live (`GET /repos/{o}/{r}/installation`, `GET /repos/{o}/{r}`, the permission call above) and builds the stored URL and default branch from GitHub's answer; any failure denies. The former sign-in snapshot table `app.user_repositories` is deprecated (UI migration `0009`): no longer read or written, kept for rolling upgrades, to be dropped later. Set the App's **Setup URL** to `<public>/login/github?refresh=1` with "Redirect on update" enabled so users land back in enzarb after installing.
- **Designer saves (ADR-0029 §4):** the Modes and Workflows tabs read `.ez/modes.toml` (and `.ez/workflows.toml`) from a Project repository's default branch and commit it back with the contents API (`GET`/`PUT /repos/{o}/{r}/contents/<path>`; message `chore(ez): update <path> from enzarb` unless the user writes one; the workflows file is validated against the branch's modes and never committed with errors), using an installation token down-scoped to that repository (`contents: read`, then `contents: write`). Before reading and again before every commit the UI checks the signed-in user's write permission live (the permission call above); the default branch is the one GitHub reports at that moment. Each commit names the blob sha the edit started from, so a file changed meanwhile fails with a conflict instead of being overwritten. Commits are authored by the App and carry `Co-authored-by: <login> <<github id>+<login>@users.noreply.github.com>`. A branch protected against the App refuses the commit (shown to the user).
- **Registration manifest:** `docs/github-app.yml` (setup in `docs/dev.md`). The same App also provides UI login (user authorization): its callback is `<public>/login/github/callback` (`callback_urls` in the manifest) and its Client ID/secret are the UI's `GITHUB_OAUTH_CLIENT_ID`/`GITHUB_OAUTH_CLIENT_SECRET`.

## 14. Web Push (device subscriptions)

The UI is an installable PWA (`/manifest.webmanifest`, service worker `service-worker.js`) and can register devices for Web Push (VAPID). The infrastructure is kept for generic use; no event is turned into a notification at the moment except the test notification. Additive: nothing here changes an existing interface.

- **Tables (`app`).** `app.push_subscriptions(id, owner, endpoint unique, p256dh, auth, categories text[], user_agent, created_at, last_used_at)`: one row per device, `owner` is the GitHub login (no FK). `app.push_sent` is a sent-log used to de-duplicate across pods. `enzarb_ui` has no privilege on either table.
- **`app_api` functions** (`SECURITY DEFINER`, all taking the owner, which the UI passes from the session login, never from client input; `EXECUTE` granted to `enzarb_ui` only): `push_subscription_upsert`, `push_subscription_list`, `push_subscription_targets`, `push_subscription_set_categories`, `push_subscription_delete`, `push_subscription_touch`, `push_claim`, `push_claim_release` and `push_sent_prune`.
- **Secret.** `enzarb-vapid-key` (data keys `public-key`, `private-key`, base64url), created once by a chart pre-install/pre-upgrade Job running the UI image (`scripts/vapid-secret.ts`) and never replaced; `secrets.vapidKey.existingSecret` names your own. Only the `enzarb-ui` Deployment reads it (optional `secretKeyRef`s, so pods start without it, with notifications off). Changing the keypair invalidates every existing browser subscription.
- **Remote functions** (`ui/src/lib/push.remote.ts`): `getPushState` (public key and the caller's devices), `subscribe`, `unsubscribe`, `sendTest` (rate limited to one per 10 s per user per pod). The service worker never caches `/_app/remote`, `/live/`, non-GET requests or navigation responses.

## Tracks API (additive)

Cluster-internal HTTP API of `enzarb-tracks` ([ADR-0029](adr/0029-ez-workflows.md)), called only by the ui server after its own access check; there is no Gateway route. Every `/v1` route needs `Authorization: Bearer $ENZARB_TRACKS_TOKEN`; errors are `{"error": {"code", "message"}}` (plus `issues` on 422 `invalid_modes`). Routes: `GET /v1/modes/catalog`, `POST /v1/modes/{parse,validate,render}`, `POST /v1/workflows/{check,render}` and `POST /v1/dry-run` (events passed inline as `{id, event, action?, payload}` rows of `connectors.event_v`, and/or `event_ids` that tracks reads from `connectors.event_v` itself when routing is on; 1-50 per request in total) and `GET /v1/decisions?event_ids=1,2,3` (1-200 ids; `{decisions: [{event_id, repo, project, sha, outcome, matched, reasons, errors, decided_at}]}`, events with no decision yet are absent; 503 `routing_disabled` without routing). Request and response shapes are in the [tracks README](../tracks/README.md). Changes are additive: new fields are optional and consumers ignore unknown ones.
